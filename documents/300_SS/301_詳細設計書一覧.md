## 2. 詳細設計原則

- Caddy -> Web Java -> Artemis -> API Java -> PostgreSQL/local fileの責務境界を維持する。
- Web Javaから業務schemaへの直接accessを禁止し、Web/API間の全業務通信をJMS `BytesMessage`固定長電文とする。
- 256 byte共通header、64 layout、画面URL・項目・表示順、role/owner scope、通知・質問・回答lifecycleを変更しない。
- 現行14画面、21 GET mapping、14 template、検索100件page、media/Range、表示順をCharacterization Testの比較対象として維持する。
- 外部仕様を変えない実装判断は`SS-D-*`として根拠と理由を本文へ記録する。上位資料変更が必要な場合はQA/RDF/UICを先に起票する。
- Class、method、DDL、設定、test観点には関連UI設計項目とRD要件IDを付け、要件 -> UI -> SS -> PG/PT/ITのchainを維持する。
- 詳細設計工程ではproduction code、DDL file、systemd unit、test codeを作成しない。Markdown設計書と整合監査だけを成果物とする。

## 6. SS設計判断の記録規則

上位資料の外部仕様を変えない具体化は、各文書で次の形式により管理する。

| 項目 | 記載内容 |
|---|---|
| ID | `SS-D-001`から本工程内一意に採番 |
| 判断 | 採用する具体的なclass、method、設定、物理型、timeout等 |
| 根拠 | UI文書番号・節、RD要件ID、現行source/資料 |

| 影響 | PG/PT/IT、設定、migration、runbookへの引継ぎ |
