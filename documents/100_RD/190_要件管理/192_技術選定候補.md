# 技術選定候補

## 1. 判定区分

導入コストは、ライセンス費だけでなく、実装、常駐resource、構築、監視、version更新、障害対応を含めて
低・中・高の3段階で評価する。本書の候補は未確定であり、未決事項への回答と試験結果をもって確定する。

## 2. Java・アプリ基盤

| 項目 | 推奨候補 | 理由 | 導入コスト |
|---|---|---|---|
| JDK | Ubuntu 26.04のOpenJDK 25 | OS package管理とsecurity updateを利用でき、指定要件を満たす。 | 低 |
| Spring Boot | 4.1系の導入時点安定版 | Java 25をsupport範囲に含み、Actuator、Security、Artemis/JMS連携を利用できる。現行3.3からはmajor migrationとなる。 | 中 |
| Build | Maven Wrapper + Java Toolchain | 開発機と本番でMaven/JDK差異を抑え、再現可能なbuildにする。 | 低 |

参考:

- [Ubuntu 26.04 openjdk-25-jdk](https://packages.ubuntu.com/resolute/openjdk-25-jdk)
- [Spring Boot System Requirements](https://docs.spring.io/spring-boot/system-requirements.html)

## 3. MQ

| 項目 | 推奨候補 | 理由 | 導入コスト |
|---|---|---|---|
| Broker | Apache ActiveMQ Artemis | JMS/AMQP、永続Queue、Request/Reply、DLQ、再配送、管理機能を持ち、今回のJava中心構成に適合する。 | 中 |
| 構成 | 単一standalone Broker | 最大10利用者、16GB RAM、単一物理hostという条件で複数Broker HAの効果より運用負荷が大きい。 | 低～中 |
| 永続化 | File Journal | Artemisが推奨する成熟した方式で、JDBC Storeよりmessage用途の性能に適する。 | 低 |
| 管理 | systemd + 管理console + metrics | 再起動、Queue滞留、DLQ、Consumer状態を管理できる。 | 中 |

Artemisの現行配布版はJava 17以上を互換対象としているため、Java 25上の起動、永続化、再配送、
planned rebootを結合試験で確認して採用する。

参考:

- [Apache ActiveMQ Artemis downloads and Java compatibility](https://activemq.apache.org/components/artemis/download)
- [Artemis Persistence](https://activemq.apache.org/components/artemis/documentation/latest/persistence.html)
- [Artemis Management Console](https://activemq.apache.org/artemis/docs/latest/management-console.html)

## 4. PostgreSQL

| 候補 | 評価 | 導入コスト |
|---|---|---|
| PostgreSQL 18 latest minor | 採用。現行DDLも18由来であり、公式support期限は2030年11月。major migration差分を抑えられる。 | 低 |
| PostgreSQL 17 latest minor | 安定した選択だが、現行18から下げる積極的理由がない。 | 中 |
| PostgreSQL 19 beta/初期版 | 要件定義時点ではbetaであり、安定性優先方針に合わない。 | 高 |

minor versionは固定せず、構築時点の18系最新security/bug-fix releaseを採用し、構築記録で確定する。

参考: [PostgreSQL Versioning Policy](https://www.postgresql.org/support/versioning/)

## 5. 認証・認可

| 候補 | 長所 | 短所 | 導入コスト | 初期評価 |
|---|---|---|---|---|
| PostgreSQL保存のアプリ内認証 | 追加daemon不要、少人数に適する、Spring Securityでhash・roleを管理できる。 | SSO/MFAや他システム連携を独自に追加する必要がある。 | 低～中 | 採用 |
| Keycloak等のOIDC IdP | 標準SSO、MFA、role管理、将来の複数アプリ連携に強い。 | 常駐service、DB、backup、upgrade、障害切分けが増える。単一アプリ・10名以下には過大になりやすい。 | 中～高 | 将来候補 |
| 平文account file | 実装が最小。 | passwordの安全な保存、account管理、監査、複数instance対応に弱い。 | 低 | 不採用候補 |

認証要求をMQ経由でAPI側認証Application Serviceへ送り、PostgreSQL上のaccountをSpring Securityで認証する。
`DelegatingPasswordEncoder`形式のone-way hashとUSER/ADMIN roleを使用する。

参考: [Spring Security Password Storage](https://docs.spring.io/spring-security/reference/features/authentication/password-storage.html)

## 6. ログ・監視

| 候補 | 内容 | 導入コスト | 初期評価 |
|---|---|---|---|
| 最小構成 | JSON file/journald、Logrotate、Actuator、Artemis console、DB統計 | 低 | 必須 |
| Prometheus + Grafana | JVM、HTTP、Hikari、PostgreSQL、host、Artemis Queueを時系列監視する。保存期間・容量上限が必要。 | 中 | 推奨候補 |
| OpenSearch/ELK | 大量logの全文検索とdashboard。 | 高 | 現規模では不採用 |

Prometheus/Grafanaは有用だが、単一SSDに保存するため、15日程度の保存期間と容量上限を設定し、
負荷・memory使用量を総合試験で確認する。

### 6.1 最小構成とPrometheus/Grafanaの差

| 観点 | 最小構成 | Prometheus/Grafana追加 |
|---|---|---|
| 現在状態 | Actuator、Artemis console、PostgreSQL統計、systemdで確認可能 | 同左 |
| 過去推移 | 構造化logから個別調査する。連続graphは持たない | CPU、memory、disk、JVM、HTTP応答、DB pool、Queue滞留等を時系列graphで確認可能 |
| 障害分析 | 発生時刻のlogを横断して調査 | 異常発生前後のmetric変化とlogを突合しやすい |
| Alert | systemd失敗や個別scriptによる限定的な検知 | Prometheus ruleで閾値判定できる。通知先連携は別途必要 |
| 常駐component | 追加の監視daemonを最小化 | Prometheus、Grafana、host/DB等のexporterと保存領域が増える |
| 運用 | Log rotation、health check、管理console中心 | 上記にdashboard、scrape設定、保存容量、認証、backup不要データの清掃、version更新が加わる |
| 導入コスト | 低 | 中 |

最大10利用者の処理性能自体にはPrometheus/Grafanaは必須ではない。15日分のgraphによる原因分析や能動的alertを
必要とするかを基準に採否を決める。

参考:

- [Spring Boot Observability](https://docs.spring.io/spring-boot/reference/actuator/observability.html)
- [Prometheus Storage](https://prometheus.io/docs/prometheus/latest/storage/)

## 7. Git・CI/CD

| 候補 | 長所 | 短所 | 導入コスト | 初期評価 |
|---|---|---|---|---|
| GitHub private repository + GitHub-hosted Actions | 本番serverの常駐resource不要。push/PRでbuild・test可能。 | sourceを外部serviceへ保存する。internet依存。 | 低 | Repository作成後の推奨 |
| local Git + 別machineのself-hosted runner | sourceをlocal管理できる。 | runner machine、patch、資格情報、job隔離を管理する必要がある。 | 中 | 代替候補 |
| local Git + 同一本番serverで手動verify | 最小構成。 | 真のCIではなく、本番resourceとbuildを競合し、release前検知が弱い。 | 低 | 暫定のみ |
| Self-managed GitLabを同一serverへ導入 | Git、review、CIをlocal完結できる。 | GitLab公式baselineが16GB RAMで、本番全体16GBの今回構成には不適。 | 高 | 不採用 |

大容量素材はGitへ格納せず、hash manifest、DB生成処理、配置・検証scriptだけを管理する。

参考:

- [GitHub-hosted runners](https://docs.github.com/en/actions/reference/runners/github-hosted-runners)
- [GitLab installation requirements](https://docs.gitlab.com/install/requirements/)
