# 互換性・受入要件

## 1. 基本方針

| ID | 要件 |
|---|---|
| TST-001 | 現行実装を正として、NK着手前に主要挙動のCharacterization Testを作成する。 |
| TST-002 | 画面デザイン、画面遷移、検索結果、並び順、ページング、メディア操作および主要エラーを比較する。 |
| TST-003 | 内部クラス構成、SQLおよびファイルパスの一致は受入条件としない。 |
| TST-004 | 現行から必要な変更は差異一覧へ記録し、理由と影響を確認した上で受け入れる。 |
| TST-005 | 現行URLおよびbookmarkの互換性は受入条件としない。画面デザイン、遷移および業務挙動を比較対象とする。 |

## 2. 試験段階

| ID | 段階 | 主対象 |
|---|---|---|
| TST-101 | 単体試験（PT） | DTO変換、電文、業務処理、SQL、ファイル解決、冪等性 |
| TST-102 | 結合試験（IT） | Web-Artemis-API-PostgreSQL-ファイルの接続と障害系 |
| TST-103 | 総合試験（ST） | 現行互換性、性能、再起動、移行、運用、セキュリティ |

## 3. MQ固有試験

- 同一メッセージの重複配送
- Consumer処理中断と再配送
- 応答timeout後の遅延応答
- DLQへの移送と再処理
- Broker停止・再起動
- API停止中のQueue滞留
- 計画再起動を跨ぐ非同期要求
- correlation IDの誤対応防止
- 固定長電文の最小値、最大値、未設定値、multibyte境界
- 規定byte数超過、途中欠損、layout version不一致
- Header長、固定data長、record長、record件数および電文総長の不整合
- 文字・数値・booleanの充填文字、全充填の未設定値および変換例外
- 固定長変換・protocol error時のJava process非正常終了、systemd再起動および後続正常処理
- 一時障害の最大3回再配送、恒久的protocol errorの再試行なしDLQ隔離
- 同期画面処理が原則1要求・1応答の2通で完了し、取得完了用の第3の業務電文を発生させないこと
- 非同期受付が1要求・1受付応答とAPI内部処理Queue 1通で開始され、完了pushを行わないこと
- MQ media descriptorからのlocal file解決とRange配信
- 大容量結果file descriptor、許可root検証、byte長・SHA-256検証および作成途中fileの排除
- 大容量結果fileを日中削除せず、次回朝batchで一括削除すること
- 朝batch清掃の削除件数・byte数・失敗記録および再実行

## 4. 朝batch・backup試験

- 再起動後にPostgreSQL、DB backup、業務データ削除、受渡しfile清掃、Artemis、API、Web、Web入口の順で実行すること
- DB backup成功後にだけ通知、質問および回答の削除を開始すること
- DB backup失敗時は業務データ削除をskipし、失敗を記録した上で受渡しfile清掃と業務アプリ起動を継続すること
- Backupの7世代管理を行うこと
- 朝batchの二重起動防止および途中失敗後の再実行
- Backupから可変データをRTO 24時間以内に復元できること

## 5. 通知・非同期処理試験

- 受付順処理、重複配送、process再起動および処理再開
- 受付通知、処理済通知、エラー通知の一覧検索と明細表示
- 業務timeoutを設けず、待ち時間だけでエラーにしないこと
- 取消の状態遷移、所有利用者検証および重複取消
- 未処理・処理中の受付通知を保持し、取消済み受付通知を次回朝batchで削除すること
- 処理済みまたはエラーへの遷移から24時間以上経過した通知を朝batchで削除すること
- 通知情報画面に手動削除操作が存在しないこと
- 初期空回答stubによる質問保存、空回答、処理済通知および質問回答検索
- 外部AI serverへの通信が初期releaseで行われないこと
- 通知削除が質問・回答を連鎖削除しないこと
- 質問・回答の画面削除で削除済みflagと削除日時を設定し、直ちに検索・閲覧対象外となること
- 論理削除済み質問・回答を、関連通知削除後かつDB backup成功後の朝batchで物理削除すること
- USERは本人分、ADMINは全利用者分の質問・回答を検索・閲覧・削除でき、APIでも権限検証すること

## 6. 性能・基盤適合試験

- `STANDARD`監視modeで同時利用者10名がそれぞれ1件の同期要求を実行し、正常処理とmessage対応関係を確認すること
- 通常の同期画面操作の95 percentileが2.5秒以内であること
- MediaのRange応答で全file読込み完了を待たず再生開始できること
- 16GB RAMと256GB SSDの基準環境で、memory枯渇、disk枯渇および無制限なQueue成長を発生させないこと
- Ubuntu Server 26.04 LTS、Java 25 LTS、導入時安定版Spring Boot、ArtemisおよびPostgreSQL 18の実機組合せで、起動、永続化、再配送、再起動およびbackup/recoveryが正常であること

## 7. 監視mode試験

- PG・PT・IT環境で`DEBUG`監視modeを有効化し、Prometheus/Grafanaと詳細metricを確認できること
- ST環境で`STANDARD`監視modeに切り替え、詳細監視serviceとscrapeを無効化できること
- `STANDARD`でもliveness/readiness、systemd、journald、Artemis、DBおよびdiskの最小監視を継続すること
- 監視modeを外部設定で切り替え、アプリ再buildが不要であること
- Metricとlogにpassword、認証context IDおよび質問本文を出力しないこと
