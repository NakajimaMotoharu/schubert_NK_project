# システム化方針

## 1. 目的

現行schubertの検索・閲覧・メディア利用に関する主要挙動を維持しながら、DB、OS・運用基盤、
Javaアプリケーション基盤およびアプリケーション間通信を再構築する。

## 2. 確定方針

| ID | 要件 |
|---|---|
| SYS-001 | 次期システムの名称をschubert NKとする。 |
| SYS-002 | Java 25 LTSを使用する。Ubuntu標準パッケージ`openjdk-25-jdk`で動作可能な構成とする。 |
| SYS-003 | OSはUbuntu Server 26.04 LTSとする。 |
| SYS-004 | DBMSはPostgreSQLを使用する。採用major/minorは技術選定で確定する。 |
| SYS-005 | Web層とサーバ側アプリケーション層の通信は、すべてApache ActiveMQ Artemisを介する。 |
| SYS-006 | ブラウザ向け画面デザインは極力維持する。MQ導入等に伴う必要不可欠な変更は許容する。 |
| SYS-007 | Web層より後段の内部処理方式は、利用者から見た挙動を極端に変えない範囲で変更できる。安定性を優先する。 |
| SYS-008 | 本番環境はオンプレミス、単一拠点、インターネット接続ありとする。 |
| SYS-009 | コンテナおよびKubernetesは初期前提としない。必要性が確認された場合に再評価する。 |
| SYS-010 | 大容量マスタ素材を含む業務データはローカルストレージに保持し、外部ストレージサービスを利用しない。 |
| SYS-011 | 要件定義、基本設計、詳細設計、実装、単体試験、結合試験、総合試験、リリースの順に工程を進める。 |

## 3. 想定論理構成

```text
Browser
  -> HTTPS
  -> Web Java
       -> 要求DTO/Bean
       -> 要求電文
       -> Apache ActiveMQ Artemis
            -> API Java Consumer
                 -> 要求DTO/Bean
                 -> Application Dispatcher
                 -> Application Service
                 -> PostgreSQL / Local Media
                 -> 応答DTO/Bean
            -> 応答電文
       <- Apache ActiveMQ Artemis
       <- 応答DTO/Bean
  <- HTML / Media response
```

非同期機能は、API側が受付情報を永続化した時点で受付応答を返し、後続処理を別メッセージとして継続できる構成とする。

## 4. 設計原則

- Web層、MQアダプタ、アプリケーション処理、DB・ファイルアクセスを分離する。
- HTTP用BeanとMQ電文を同一クラスへ密結合させず、境界で変換する。
- メッセージ再送を前提として、API処理を冪等にする。
- DBおよびMQ障害時に、処理結果が不明な状態を検出・回復できるようにする。
- 外部仕様の変更は互換性要件と試験結果により管理する。
