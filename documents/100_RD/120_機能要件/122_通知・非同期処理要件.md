# 通知・非同期処理要件

## 1. 基本フロー

```text
Webから非同期要求
  -> 受付完了応答
  -> 通知情報一覧で状態確認
  -> 通知情報明細で回答・エラー内容確認または取消操作
```

非同期処理は個別priorityを使用せず受付順に処理する。業務timeoutは設けず、受付済み要求はいずれ処理される前提とする。
厳密な直列処理とConsumer並列数はQA-036で確定する。

## 2. 通知表示

| ID | 要件 |
|---|---|
| NTF-001 | 通知情報一覧機能を設け、Login利用者本人の通知を検索できること。 |
| NTF-002 | 一覧で閲覧可能な通知区分は受付通知、処理済通知、エラー通知とする。 |
| NTF-003 | 受付通知は要求受付後に作成し、処理済みまたは取消済みになるまで保持する。処理中も利用者向けには受付通知として表示する。 |
| NTF-004 | 処理完了時に受付通知を処理済通知へ遷移させ、明細から回答を確認できること。 |
| NTF-005 | 処理失敗時にエラー通知へ遷移させ、明細からエラー内容を確認できること。 |
| NTF-006 | 処理済通知は、利用者が通知情報明細から取消操作を行うまで保持する。取消の意味とデータ削除範囲はQA-035およびQA-037で確定する。 |
| NTF-007 | エラー通知はエラー発生から24時間以上経過したものを、次回朝batchで削除する。 |
| NTF-008 | 一覧の検索条件、並び順、page size、表示項目および明細項目はUI工程で定義する。 |

## 3. 非同期処理制御

| ID | 要件 |
|---|---|
| ASY-001 | 非同期要求に受付ID、要求利用者、受付日時、状態、message IDおよびcorrelation IDを記録する。 |
| ASY-002 | 要求の取出し順は受付順（FIFO）とし、priorityによる追越しを行わない。 |
| ASY-003 | 業務timeoutを設けず、処理待ち時間または処理時間だけを理由にエラーへ遷移させない。 |
| ASY-004 | Process再起動やMQ再配送後も、冪等性を維持して処理を再開できること。 |
| ASY-005 | 取消操作はAPI Java側で対象利用者と現在状態を検証し、重複取消を冪等に扱う。詳細な状態遷移はQA-035で確定する。 |
| ASY-006 | 通知レコードと将来の質問・回答等の業務データを分離し、通知取消時の業務データ保持方針をQA-037で確定する。 |

## 4. 初期release範囲

AIモデル、AI質問固有入力項目および回答生成処理は初期release対象外である。
通知情報一覧、通知情報明細、取消操作および通知永続表を初期releaseへ含めるかはQA-034で確定する。
