# 通知・非同期処理要件

## 1. 基本フロー

```text
Webから非同期要求
  -> 受付完了応答
  -> 通知情報一覧で状態確認
  -> 通知情報明細で回答・エラー内容確認または取消操作
```

非同期処理は個別priorityを使用せず受付順に処理する。Consumer並列数は1とし、1件ずつ直列処理する。
NK側に業務timeoutは設けない。

## 2. 通知表示

| ID | 要件 |
|---|---|
| NTF-001 | 通知情報一覧機能を設け、Login利用者本人の通知を検索できること。 |
| NTF-002 | 一覧で閲覧可能な通知区分は受付通知、処理済通知、エラー通知とする。 |
| NTF-003 | 受付通知は要求受付後に作成し、処理済み、エラーまたは取消済みに状態遷移するまで保持する。処理中も利用者向けには受付通知として表示する。 |
| NTF-004 | 処理完了時に受付通知を処理済通知へ遷移させ、明細から回答を確認できること。 |
| NTF-005 | 処理失敗時にエラー通知へ遷移させ、明細からエラー内容を確認できること。 |
| NTF-006 | 処理済通知は取消および手動削除不可とし、利用者が回答通知の明細を閲覧できること。処理済み遷移から24時間以上経過後の朝batchで自動削除する。 |
| NTF-007 | エラー通知はエラー発生から24時間以上経過したものを、次回朝batchで削除する。 |
| NTF-008 | 一覧の検索条件、並び順、page size、表示項目および明細項目はUI工程で定義する。 |
| NTF-009 | 受付通知とエラー通知を利用者が手動削除できないこと。未処理および処理中の受付通知は朝batchでも削除せず、状態確認のため保持する。 |
| NTF-010 | 受付中の通知明細では処理取消を実行できること。処理中、処理済みおよびエラーでは処理取消を許可しない。 |
| NTF-011 | 取消済みとなった受付通知は、次回朝batchで自動削除する。 |
| NTF-012 | 通知情報画面に手動削除操作を設けない。質問・回答の削除は質問回答一覧・明細から行う。 |

## 3. 非同期処理制御

| ID | 要件 |
|---|---|
| ASY-001 | 非同期要求に受付ID、要求利用者、受付日時、状態、message IDおよびcorrelation IDを記録する。 |
| ASY-002 | 要求の取出し順は受付順（FIFO）、Consumer並列数は1とし、priorityによる追越しを行わない。 |
| ASY-003 | NK側に業務timeoutを設けず、処理待ち時間または処理時間だけを理由にエラーへ遷移させない。 |
| ASY-004 | Process再起動やMQ再配送後も、冪等性を維持して処理を再開できること。 |
| ASY-005 | 受付中だけ処理取消を許可する。API Javaが所有利用者と状態を検証し、重複取消を冪等に扱う。 |
| ASY-006 | 処理開始後は取消操作を許可しない。処理済みでは回答通知の閲覧だけを許可し、通知は日次自動削除に委ねる。 |
| ASY-007 | 外部AI server連携後は、処理中要求に対する正常終了通知またはエラー通知を受信するまで次の要求を処理しない。 |
| ASY-008 | 外部AI serverから応答がない場合のtimeout、skipおよび強制error遷移は初期要件に含めず、将来の変更管理対象とする。 |
| ASY-009 | 通知レコードと質問・回答データを分離し、通知削除が質問・回答を連鎖削除しないこと。 |

## 4. 初期release範囲

通知情報一覧、通知情報明細、受付中の取消操作、通知永続表、質問要求、質問受付完了および質問回答一覧検索を
初期releaseへ含める。外部AI serverとの送受信処理だけを未実装とする。

初期releaseでは質問受付時に質問と受付通知を保存し、内部非同期処理Queueへ登録して受付完了を返す。直列Consumerは空文字列の回答を作成して速やかに処理済みへ遷移させ、処理済通知を作成する。
この空回答stubは将来のAI server連携部品と交換可能な境界に配置する。
