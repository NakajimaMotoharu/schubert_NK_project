# 共通固定長電文方式要件

## 1. 電文構造

MQ bodyは、固定長の共通header、機能別固定dataおよび0件以上の同一layout固定長recordから構成する。
各項目および各recordは固定長であるが、電文総長はrecord件数に応じて変わる。

```text
電文総長 = header長 + 固定data長 + (反復record長 × record件数)
```

反復recordを持たない電文では、反復record長とrecord件数をともに0とする。
例としてheader 100 byte、固定data 25 byte、反復record 25 byteの場合、record件数1、2、3の電文総長は
それぞれ150、175、200 byteとなる。これらの数値は構造説明用であり、実際の長さはUI工程のinterface項目仕様で決定する。

## 2. 項目表現規則

| ID | 要件 |
|---|---|
| MSG-001 | bodyはJMS `BytesMessage`に格納し、全業務項目をUTF-8の文字列表現で送受信する。 |
| MSG-002 | 項目長は文字数ではなくUTF-8 encode後のbyte数とする。 |
| MSG-003 | 文字項目は値の右側をASCII spaceで充填する。 |
| MSG-004 | 数値項目は原則必須とし、値の左側をASCII `0`で充填する。符号、小数点およびscaleが必要な項目はinterface項目仕様で個別に定義する。 |
| MSG-005 | 非必須で数値を扱う項目は文字項目として定義し、値を左寄せして右側をASCII spaceで充填する。例えば6 byteの値123は`123   `とし、全byte spaceを未設定として扱う。 |
| MSG-006 | BooleanはASCII文字`0`または`1`の1 byteで表現する。 |
| MSG-007 | 規定byte数超過時は共通変換部品が変換例外を発生させ、切捨て、UTF-8途中切断および送信を行わない。 |
| MSG-008 | CR、TABおよびNULは原則禁止する。業務項目内の改行は初期電文で使用しない。将来使用する場合はLFだけを許容する。 |
| MSG-009 | 文書、設定および生成fileの改行codeはLFを標準とする。 |
| MSG-010 | 電文化する文字列をUnicode NFCで正規化する。NFC正規化はbyte長判定より前に行う。 |
| MSG-011 | 電文日時は日本標準時（Asia/Tokyo）の`yyyyMMddHHmmssSSS`形式で表現する。 |

Unicodeでは、見た目が同じ文字を異なるcode point列で表現できる場合がある。例えば「ガ」には合成済みの1文字と、
「カ」に結合用濁点を続ける表現があり、UTF-8のbyte列とbyte数が異なる。NFCはこれらを可能な範囲で合成済み表現へ
統一し、固定byte長判定、DB検索および一致判定の揺れを抑える。採用時はNFC正規化、byte長判定、充填の順に処理する。

## 3. 共通header項目（QA-020確定）

次の項目を共通headerに持たせる。各byte長、開始位置およびheader総byte長はUI工程で決定する。

| 項目 | 用途 | 要求・応答での扱い |
|---|---|---|
| Protocol識別子 | Schubert NK電文以外の誤投入検知 | 常時必須 |
| 共通header version | header layoutの互換性判定 | 常時必須 |
| Data layout ID | 機能別要求・応答layoutの識別 | 常時必須 |
| Data layout version | 機能別data layoutの互換性判定 | 常時必須 |
| 要求・応答区分 | Request、Responseの識別 | 常時必須 |
| 同期・非同期区分 | 同期要求、非同期受付、内部非同期処理の識別 | 常時必須 |
| Message ID | 電文を一意に識別し、重複を検出 | 常時必須 |
| Correlation ID | 要求、応答および後続処理の対応付け | 常時必須 |
| 送信日時 | timeout、追跡および監査 | 常時必須。日本標準時の`yyyyMMddHHmmssSSS` |
| 認証context ID | API側で利用者sessionとroleを再検証 | 利用者起点電文で必須。固定長の不透明ID |
| Header長 | header layoutと実byte位置の検証 | 常時必須 |
| 固定data長 | 反復recordより前の機能別data長 | 常時必須 |
| 反復record長 | 反復1 record当たりのbyte長 | 反復なしは0 |
| Record件数 | bodyに含む反復record件数 | 反復なしは0 |
| 電文総長 | body全体のbyte長 | 常時必須 |
| 処理結果code | 成功、業務error、system error等の機械判定 | 応答で設定、要求では充填文字 |
| 予約領域 | 将来追加に備えた互換領域 | 常時充填文字、用途変更時はversion更新 |

MQ側が持つJMS Message ID/Correlation IDと業務header内の値は相互に照合する。
Queue名、reply先およびMQ資格情報は業務bodyへ含めず、MQ設定・propertyで管理する。

## 4. 受信検証

受信側は業務処理の開始前に、少なくとも次を検証する。

1. Protocol識別子と対応versionが正しいこと。
2. Header、固定dataおよび反復recordの各長さが対象layout定義と一致すること。
3. 実body長とheaderの電文総長が一致すること。
4. `header長 + 固定data長 + (反復record長 × record件数)`が電文総長と一致すること。
5. Record件数と電文総長が対象interfaceごとに定めた上限以内であること。
6. 必須項目、文字種、数値、boolean、制御文字およびUTF-8が正しいこと。
7. JMS propertyと業務headerのmessage IDおよびcorrelation IDが対応すること。

検証不合格時は対象の業務処理を開始せず、致命的protocol errorとして当該Java processを非正常終了させる。
Systemdは非正常終了を検知してJavaアプリを再起動する。一時障害は最大3回再配送し、上限超過後にDLQへ隔離する。
Version不一致等の再試行しても解消しないprotocol errorは再配送せずDLQへ隔離する。

## 5. 大容量結果のfile受渡し

対象interfaceの電文総長上限を超えることが設計時点で想定される場合は、API Javaが結果を専用のlocal受渡しdirectoryへ
file出力し、MQ応答ではfile descriptorだけを返す方式を使用できる。

| ID | 要件 |
|---|---|
| MSG-F01 | File本体をMQへ格納しない。MQ応答dataには固定長のfile descriptorを格納する。 |
| MSG-F02 | File descriptorは少なくとも論理file IDまたは許可root基準の相対path、file byte長、SHA-256、record長およびrecord件数を持つ。 |
| MSG-F03 | Web Javaは受取ったpathを正規化し、許可された受渡しdirectory配下であることを検証してからfileを読み込む。任意の絶対pathを許可しない。 |
| MSG-F04 | File内容は対象interfaceで定義したUTF-8固定長record形式とし、Web Javaが同じ共通変換部品でBeanへ変換できること。 |
| MSG-F05 | File作成完了後に一時名から確定名へatomicに変更し、Web Javaが作成途中のfileを読み込まないこと。 |
| MSG-F06 | File byte長とSHA-256を照合し、不一致時は使用しない。 |
| MSG-F07 | Web Javaは取得完了ACKを送信せず、生成されたfileは取得成否にかかわらず次回朝batchまで保持する。 |
| MSG-F08 | File名または論理file IDを一意にし、同名fileを上書きしない。 |
| MSG-F09 | 朝batchは業務アプリ起動前に、処理開始時点で専用受渡しdirectoryに存在する一時fileと確定fileを一括削除し、削除件数、削除byte数および失敗を記録する。 |

### 5.1 Web Javaの取得検証と削除

Web Javaは次を検証するが、検証結果を削除条件には使用せず、API Javaへの取得完了ACKも送信しない。

1. File descriptorの論理file IDまたは相対pathが許可root配下を示すことを検証する。
2. Fileを終端まで読み込み、実file byte長とdescriptorのfile byte長を照合する。
3. SHA-256を照合する。
4. 全recordの固定長、record件数、UTF-8および項目形式を検証し、Web側Beanへの変換を完了する。
5. Fileを直接HTTP responseへstreamするinterfaceでは、Web Javaによるfile読込みとresponse出力を正常完了する。

FileはWeb Javaの取得成否やbrowser描画成否にかかわらず日中に削除しない。次回の朝batchが、業務アプリ停止中かつ
起動前に専用受渡しdirectoryを一括清掃する。これにより同期要求、同期応答以外の追加MQ通信を発生させない。
