# 共通固定長電文方式要件

## 1. 電文構造

MQ bodyは、固定長の共通header、機能別固定dataおよび0件以上の同一layout固定長recordから構成する。
各項目および各recordは固定長であるが、電文総長はrecord件数に応じて変わる。

```text
電文総長 = header長 + 固定data長 + (反復record長 × record件数)
```

反復recordを持たない電文では、反復record長とrecord件数をともに0とする。
例としてheader 100 byte、固定data 25 byte、反復record 25 byteの場合、record件数1、2、3の電文総長は
それぞれ150、175、200 byteとなる。これらの数値は構造説明用であり、実際の長さはUI工程のinterface項目仕様で決定する。

## 2. 項目表現規則

| ID | 要件 |
|---|---|
| MSG-001 | bodyはJMS `BytesMessage`に格納し、全業務項目をUTF-8の文字列表現で送受信する。 |
| MSG-002 | 項目長は文字数ではなくUTF-8 encode後のbyte数とする。 |
| MSG-003 | 文字項目は値の右側をASCII spaceで充填する。 |
| MSG-004 | 数値項目は値の左側をASCII `0`で充填する。符号、小数点およびscaleが必要な項目はinterface項目仕様で個別に定義する。 |
| MSG-005 | 未設定項目は項目種別の充填文字で全byteを充填する。数値の未設定と値0が同じ表現になる点はQA-028で確定する。 |
| MSG-006 | BooleanはASCII文字`0`または`1`の1 byteで表現する。 |
| MSG-007 | 規定byte数超過時は共通変換部品が変換例外を発生させ、切捨て、UTF-8途中切断および送信を行わない。 |
| MSG-008 | CR、TABおよびNULは原則禁止する。業務項目内の改行は初期電文で使用しない。将来使用する場合はLFだけを許容する。 |
| MSG-009 | 文書、設定および生成fileの改行codeはLFを標準とする。 |
| MSG-010 | Unicode正規化の採否はQA-019で確定する。正規化する場合はbyte長判定より前に行う。 |

Unicodeでは、見た目が同じ文字を異なるcode point列で表現できる場合がある。例えば「ガ」には合成済みの1文字と、
「カ」に結合用濁点を続ける表現があり、UTF-8のbyte列とbyte数が異なる。NFCはこれらを可能な範囲で合成済み表現へ
統一し、固定byte長判定、DB検索および一致判定の揺れを抑える。採用時はNFC正規化、byte長判定、充填の順に処理する。

## 3. 共通header項目候補

次の項目を共通headerの候補とする。項目順、各byte長およびheader総byte長はUI工程で決定する。

| 項目 | 用途 | 要求・応答での扱い |
|---|---|---|
| Protocol識別子 | Schubert NK電文以外の誤投入検知 | 常時必須 |
| 共通header version | header layoutの互換性判定 | 常時必須 |
| Data layout ID | 機能別要求・応答layoutの識別 | 常時必須 |
| Data layout version | 機能別data layoutの互換性判定 | 常時必須 |
| 要求・応答区分 | Request、Responseの識別 | 常時必須 |
| 同期・非同期区分 | 同期要求、非同期受付、内部非同期処理の識別 | 常時必須 |
| Message ID | 電文を一意に識別し、重複を検出 | 常時必須 |
| Correlation ID | 要求、応答および後続処理の対応付け | 常時必須 |
| 送信日時 | timeout、追跡および監査 | 常時必須。formatとtimezoneはQA-026で確定 |
| 認証context ID | API側で利用者sessionとroleを再検証 | 利用者起点電文で必須候補。方式はQA-030で確定 |
| Header長 | header layoutと実byte位置の検証 | 常時必須 |
| 固定data長 | 反復recordより前の機能別data長 | 常時必須 |
| 反復record長 | 反復1 record当たりのbyte長 | 反復なしは0 |
| Record件数 | bodyに含む反復record件数 | 反復なしは0 |
| 電文総長 | body全体のbyte長 | 常時必須 |
| 処理結果code | 成功、業務error、system error等の機械判定 | 応答で設定、要求では充填文字 |
| 予約領域 | 将来追加に備えた互換領域 | 常時充填文字、用途変更時はversion更新 |

MQ側が持つJMS Message ID/Correlation IDと業務header内の値は相互に照合する。
Queue名、reply先およびMQ資格情報は業務bodyへ含めず、MQ設定・propertyで管理する。

## 4. 受信検証

受信側は業務処理の開始前に、少なくとも次を検証する。

1. Protocol識別子と対応versionが正しいこと。
2. Header、固定dataおよび反復recordの各長さが対象layout定義と一致すること。
3. 実body長とheaderの電文総長が一致すること。
4. `header長 + 固定data長 + (反復record長 × record件数)`が電文総長と一致すること。
5. Record件数と電文総長が対象interfaceの上限以内であること。
6. 必須項目、文字種、数値、boolean、制御文字およびUTF-8が正しいこと。
7. JMS propertyと業務headerのmessage IDおよびcorrelation IDが対応すること。

検証不合格時は対象の業務処理を開始せず、protocol errorとして扱う。
共通headerからcorrelation ID等を安全に取得できる場合のerror応答、再配送および不正電文の保全方式は
QA-021およびQA-027で確定する。
