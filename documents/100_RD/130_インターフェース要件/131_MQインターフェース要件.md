# MQインターフェース要件

## 1. 基本方式

| ID | 要件 |
|---|---|
| MQ-001 | Web JavaとAPI Javaの要求・応答通信はApache ActiveMQ Artemisを使用する。 |
| MQ-002 | 同期画面処理はRequest/Reply方式とし、要求と応答を相関IDで対応付ける。 |
| MQ-003 | 非同期画面処理は受付結果を同期応答し、実処理は永続Queueで継続する。 |
| MQ-004 | Web Javaは業務DBへ直接アクセスせず、業務処理をAPI Javaへ要求する。利用者起点要求には認証context IDを設定し、API Javaがsessionとroleを検証する。 |
| MQ-005 | API Javaは要求種別から該当Application Serviceへ処理を振り分ける。 |
| MQ-006 | メッセージに一意なmessage ID、correlation ID、message type、schema version、送信日時を持たせる。 |
| MQ-007 | 業務メッセージは永続化し、API側は手動ACKを使用する。ACKは必要な業務処理の確定後に行う。 |
| MQ-008 | API側Consumerはat-least-once配送および再配送を前提として冪等に処理する。 |
| MQ-009 | 再配送回数を超えたメッセージはDead Letter Queueへ移送し、運用者が確認・再処理できること。 |
| MQ-010 | 同期要求には有効期限を設け、期限切れ要求および遅延応答を識別・廃棄できること。 |
| MQ-011 | Web/API間でJavaクラスを直接serializeした形式を使用しない。言語・版に依存しない電文形式を使用する。 |
| MQ-012 | MQ接続先、認証情報、Queue名およびタイムアウトを外部設定可能にする。 |
| MQ-013 | Artemisの管理ポートおよびMQ acceptorをインターネットへ直接公開しない。 |
| MQ-014 | MQで送受信する業務電文は、固定長の共通header部、機能別固定data部および0件以上の固定長反復record部から構成する。電文総長はrecord件数に応じて可変とする。 |
| MQ-015 | header部はすべての要求・応答電文で同じlayoutおよび同じ型を使用する。 |
| MQ-016 | data部は画面要求と画面応答ごとに個別のBean/DTO型を定義する。 |
| MQ-017 | 各電文項目に開始byte位置、byte長、順序、型、必須、padding、許容値を定義する。 |
| MQ-018 | 文字項目はUTF-8でencodeする。項目長は文字数ではなくencode後のbyte数で判定する。 |
| MQ-019 | 動画、音声、音楽等の非text素材本体をMQ messageへ格納しない。 |
| MQ-020 | Media APIはMQ応答でmedia descriptorを返し、Web Javaが許可されたlocal素材をRange配信する。 |
| MQ-021 | Login要求もMQ経由でAPI Javaへ送り、API JavaがPostgreSQLのaccountとroleを検証する。Web Javaは認証成功後のsessionを管理する。 |
| MQ-022 | MQ message headerと業務電文headerのmessage ID/correlation IDを対応付け、不一致をerrorとする。 |
| MQ-023 | 業務電文はJMS `BytesMessage`で送受信し、bodyは定義済みUTF-8 byte列だけを格納する。 |
| MQ-024 | 数値およびbooleanを含む全項目を文字列表現としてencodeし、Java primitive値のbinary表現を格納しない。 |
| MQ-025 | 文字項目は右側をASCII space（`0x20`）、数値項目は左側をASCII `0`（`0x30`）で規定byte長まで充填する。 |
| MQ-026 | 未設定項目は、その項目に定義された充填文字で全byteを充填する。 |
| MQ-027 | Boolean項目は文字`0`をfalse、文字`1`をtrueとして格納し、それ以外を変換errorとする。 |
| MQ-028 | 規定byte数を超過した場合、共通変換部品が変換例外を発生させ、切捨ておよび不完全な電文送信を行わない。 |
| MQ-029 | CR、TABおよびNULを業務項目内で原則禁止する。業務電文内の改行は初期要件では定義せず、将来必要になった場合はLFだけを許容する。 |
| MQ-030 | 共通headerに固定data長、反復record長、record件数および電文総長を持たせ、受信時に実body長との整合を検証する。 |
| MQ-031 | UTF-8の複数byte文字を項目境界で分割しない。encode後のbyte数が規定値以下であることを確認してから充填する。 |
| MQ-032 | 固定長変換例外または未対応layout versionを検知したJavaアプリは、業務処理を実行せず非正常終了する。Systemdは非正常終了を検知して当該アプリを再起動する。 |
| MQ-033 | 電文化する文字列はNFC正規化後にUTF-8 byte長を検査し、規定長まで充填する。 |
| MQ-034 | 数値項目は原則必須とする。非必須の数値相当項目は文字項目として定義し、右space充填、全spaceを未設定とする。 |
| MQ-035 | 電文日時は日本標準時の`yyyyMMddHHmmssSSS`形式とする。 |
| MQ-036 | 利用者起点のMQ要求は固定長の認証context IDを持ち、API JavaがDB上のsession有効性とroleを要求ごとに検証する。 |
| MQ-037 | 反復record件数と電文総byte数の上限をinterfaceごとに定義し、上限超過を固定長変換例外とする。 |
| MQ-038 | 1電文が持つ反復record layoutは1種類・1領域までとし、複数の一覧は別電文または別interfaceへ分割する。 |
| MQ-039 | 電文総長が過大になるinterfaceは、API Javaが専用local directoryへ結果fileを出力し、MQでは固定長file descriptorだけをWeb Javaへ連携できる。 |
| MQ-040 | 一時障害は最大3回再配送し、上限超過後にDLQへ隔離する。Version不一致等の恒久的protocol errorは再試行せずDLQへ隔離する。 |
| MQ-041 | 大容量結果fileの取得完了ACKは送信しない。Fileは取得成否にかかわらず日中保持し、次回朝batchで一括削除する。 |
| MQ-042 | 質問要求、受付完了、通知一覧・明細、受付取消、質問回答検索・閲覧・削除のWeb/API間通信をMQ固定長電文として定義する。通知の手動削除電文は設けない。 |
| MQ-043 | 初期releaseのAPI Javaは質問要求を保存して内部非同期処理Queueへ登録し、受付完了応答を返す。直列Consumerは外部AI serverへ送信せず空回答を作成し、処理済通知へ遷移させる。 |
| MQ-044 | 同期画面処理1回のWeb/API間業務電文は、原則として要求1通と応答1通の計2通とする。JMS ACK、broker内部制御および障害時再配送は業務電文数に含めない。 |
| MQ-045 | 非同期受付1回のWeb/API間業務電文は要求1通と受付応答1通の計2通とし、API内部の非同期処理Queueへ1通を登録する。完了push電文は設けず、利用者の通知検索は通常の要求・応答とする。 |

## 2. 初期構成案

- 単一Artemis Broker
- 永続File Journal
- 同期要求Queue、同期応答Queue、非同期処理Queue、DLQ、Expiry Queueを分離
- Web/APIごとに異なるMQユーザーと最小権限を付与
- systemdによる自動起動・異常終了時再起動

本案は同時利用者最大10名程度と16GB RAMの単一物理サーバに合わせたものである。

## 3. 固定長電文の設計方針

- UTF-8の複数byte文字を項目途中で切断しない。
- 規定byte長を超える値を暗黙に切り捨てず、電文作成errorとする。
- layout変更時はschema versionを変更し、異なるversionを誤解釈しない。
- 予約領域を設ける場合もbyte位置と初期値を定義する。
- 項目byte長は現行実データの最大UTF-8 byte数を計測し、業務上の上限と将来余裕を加えて決定する。
- UI工程で、要求・応答ごとのinterface項目仕様を作成する。
- 詳細な共通規則および確定したheader項目は`132_共通固定長電文方式要件.md`に定義する。

## 4. Dead Letter Queueの位置づけ

Dead Letter Queue（DLQ）は、変換error等で正常処理できず、再配送しても成功しない電文を通常Queueから隔離して
保全するためのQueueである。業務処理の成功扱いにはせず、後続の正常電文が同じ不正電文に妨げられることを防ぐ。
一時障害は最大3回再配送し、上限超過後にDLQへ隔離する。Version不一致等の恒久的protocol errorは再試行せず
DLQへ隔離する。

## 5. 後続工程で具体化する設計事項

次は要件の未決事項ではなく、本書の方式・上限・障害時原則に従ってUIまたはSS工程で具体値と実装方式を定める。

- 共通header各項目のbyte位置、byte長および総byte長（UI工程）
- destinationおよびreply queueの具体構成
- 同期要求timeoutと再試行
- DB更新とMQ送信の整合方式
- 順序保証が必要な業務単位
