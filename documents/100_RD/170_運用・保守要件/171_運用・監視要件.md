# 運用・監視要件

## 1. 運用

| ID | 要件 |
|---|---|
| OPS-001 | PostgreSQL、Artemis、API Java、Web JavaおよびCaddy等の入口をsystemdで管理する。 |
| OPS-002 | 起動、停止、再起動、状態確認およびログ確認手順をスクリプト化する。 |
| OPS-003 | 毎日05:00頃のSSH経由運用処理に対応する。停止順、起動順、timeoutおよび失敗時動作を定義する。 |
| OPS-004 | OS、JDK、PostgreSQL、Artemisおよびアプリのversionを記録し、再現可能にする。 |
| OPS-005 | 秘密情報をGitへ登録しない。環境別設定と秘密情報を分離する。 |
| OPS-006 | 緊急度評価に基づくsecurity updateの選定と臨時適用は別projectの所管とし、本projectではsecurity専用の適用機能を開発しない。OPS-008の日次一般updateに、構成済みrepositoryから配布されるsecurity修正が含まれることは許容する。 |
| OPS-007 | 別projectによるsecurity update後に再起動が必要な場合は、本projectの計画停止・起動手順と連携できること。 |
| OPS-008 | 一般package updateは毎日05:00頃の計画停止中に`apt update`および`apt upgrade`で適用する。実行結果と変更packageを記録する。 |
| OPS-009 | 再起動後は、PostgreSQL起動、DB backup、業務データ削除、受渡しfile清掃、Artemis、API Java、Web Java、Web入口の順に依存関係を制御して起動する。 |
| OPS-010 | Backupその他の固定時刻業務処理を朝batchへ集約し、個別処理ごとの開始・終了・処理件数・成否を記録する。 |
| OPS-011 | 朝batchおよび業務アプリ起動処理は二重起動を防止し、途中失敗後に安全に再実行できること。 |
| OPS-012 | Web/API Javaの非正常終了をsystemdで検知し、終了codeと原因を記録した上で自動再起動する。短時間の無制限再起動を防ぐrate limitも設定する。 |
| OPS-013 | 朝batchは業務アプリ起動前に大容量結果file専用directoryを一括清掃し、削除件数、削除byte数および失敗fileを記録する。 |
| OPS-014 | 朝batchは、処理済みまたはエラーへの遷移から24時間以上経過した通知を削除し、対象件数、削除件数および失敗を記録する。 |
| OPS-015 | 朝batchは取消済み受付通知を削除する。未処理および処理中の受付通知は削除しない。 |
| OPS-016 | 朝batchは、論理削除済みかつ関連通知が存在しない質問・回答を物理削除する。 |
| OPS-017 | DB backupが失敗した場合はOPS-014～OPS-016の業務データ削除を実行せず、失敗を記録した上で受渡しfile清掃と業務アプリ起動を継続する。 |

## 2. 監視・ログ

| ID | 要件 |
|---|---|
| MON-001 | Web、API、DBおよびMQのliveness/readinessを個別確認できること。 |
| MON-002 | HTTP request IDとMQ correlation IDを対応付け、WebからAPIまで追跡できること。 |
| MON-003 | 構造化アプリログ、認証・操作監査ログ、MQ処理ログを記録する。 |
| MON-004 | password、MQ/DB資格情報およびsession tokenをログへ出力しない。 |
| MON-005 | Queue滞留数、処理率、再配送数、DLQ件数、Consumer接続状態を確認できること。 |
| MON-006 | JVM、heap、GC、DB connection pool、ディスク残量およびHTTP応答時間を確認できること。 |
| MON-007 | ログおよびmetricに保存期間と容量上限を設定し、SSD枯渇を防ぐこと。 |
| MON-008 | 固定長変換・protocol errorによるJava process終了、systemd再起動回数、再起動抑止および原因message IDを管理者が確認できること。 |
| MON-009 | 大容量結果file専用directoryのfile件数と総byte数を監視し、設計上限超過を検知できること。 |
| MON-010 | PG、PTおよびIT工程では`DEBUG`監視modeを使用し、Prometheus、Grafana、必要なexporterおよび詳細Actuator metricを有効化する。 |
| MON-011 | ST工程以降は`STANDARD`監視modeを使用し、Prometheus、Grafana、exporterおよび詳細metric収集を無効化する。Liveness/readiness、systemd、journald、Artemis管理、DB統計およびdisk監視は維持する。 |
| MON-012 | 監視modeは環境変数または外部設定fileで切替可能とし、Prometheus/Grafana等のservice起動・停止もmodeと整合させる。 |
| MON-013 | `DEBUG`監視modeとJava application log levelの`DEBUG`は別設定とし、password、質問本文等の機微情報を詳細metric・logへ出力しない。 |

常時監視はSpring Boot Actuator/Micrometer、Artemis管理機能、構造化file logまたはjournaldを使用する。
Prometheus/GrafanaはIT工程までの`DEBUG`監視modeで使用する。OpenSearch/ELKは初期構成に対して過大なため採用しない。

## 4. バックアップ運用

| ID | 要件 |
|---|---|
| BKO-001 | 可変DBデータおよび環境設定を自動バックアップする。 |
| BKO-002 | Backup先directoryを外部設定し、将来localからNASへ変更可能にする。 |
| BKO-003 | Backup成功・失敗、保存日時、対象DB versionおよびfile sizeを記録する。 |
| BKO-004 | 可変データbackupを毎朝の業務アプリ起動前に1回取得する。 |
| BKO-005 | Backupは日次7世代を保持し、RPO 24時間、RTO 24時間を目標とする。 |
| BKO-006 | 保持世代を超えたbackupは、新規backupの正常性を確認した後に世代管理処理で削除する。 |
| BKO-007 | Backup失敗時は失敗内容を記録して管理者が確認できるようにし、業務アプリの起動は継続する。 |
| BKO-008 | 当日backupの正常終了を、通知、質問および回答の物理削除を開始する前提条件とする。 |

## 5. 朝batch実行順

1. PostgreSQLを起動して接続・整合性を確認する。
2. 可変DBデータをbackupし、backup fileの作成結果を検証する。
3. Backup成功時だけ、24時間経過通知、取消済み受付通知および論理削除済み質問・回答を順序制御して削除する。
4. Backup成否にかかわらず、大容量結果file専用directoryを清掃する。
5. Artemis、API Java、Web JavaおよびWeb入口を依存順に起動する。

手順2が失敗した場合、手順3をskipして業務データを保持し、管理者が失敗を確認できるようにする。
