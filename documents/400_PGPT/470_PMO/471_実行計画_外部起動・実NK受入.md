## 2. 最初に完成させる対象

**Production外部起動 → 必須起動条件 → Login/検索/Log → 実NK CHR-A01/L01**を最初の一つの受入経路とする。既存の実HTTP/DB/Artemis接続を利用し、部品の再実装や同じ設計の再調査を避ける。R3完了後は460/SS362の依存順で次の機能へ自走を継続する。

| 段階 | 終了条件・証拠 |
|---|---|
| R0 現在地の確定 | Git/認定source/枠/既存process/元tree保全を照合。下表D01〜D07の実装先・関連SS/PT/CHR・未達条件を短く対応付ける。計画だけで終了しない |
| R1 起動経路の組立 | Web/APIの外部entrypointと起動smoke試験を先に作り、既存config・credential・DB/JMS・runtimeを組み立てる。成功時と起動途中失敗時の資源後条件を独立PTで確認 |
| R2 実プロセス起動 | 必須gateを満たした隔離PG/PT環境で、Production Web/APIを外部プロセスとして起動・停止。実PID/起動command、readiness、失敗/終了後条件のsanitized証跡を残す |

不足した必須gateを迂回して起動しない。R1の未完成段階は安全に起動拒否し「未認定」とする。実装前の赤い試験や限定成功は正式受入と別に保存する。実systemd固有条件と代替起動で確認できる条件は区別し、確認していないOS配布/権限を確認済みにしない。PG/PTに必要な実装を後続IT/STへ移さない。

## 4. 検証の区切りと正式認定

451の必須gateとcoverage100%、独立oracle、null/境界/異常/並行/再送、修正前BUG・必要YKT、Current baseline・秘密情報・traceを維持する。検証の粒度を変え、品質条件を削らない。

| 状況 | 実行・保存するもの |
|---|---|
| 部品追加・限定変更、横断影響なし | 変更moduleと依存/影響suite・必要な静的/coverageを検証。source/実行範囲/未実行範囲を暫定記録。class追加だけを理由に全scope再収集へ進まない |
| 機能の受入、変更後の停止、PR/工程gate | 451所定の全体検証と同一run/source/branchの全必須scope/hash。部分成功を正式合格へ混ぜない |
| POM・共通codec・DDL・security等の横断変更 | 451どおり全回帰を先行。名称だけで横断変更とせず、実際の変更と影響先を1行記録して判断 |
| 管理文書だけの変更/認定source等不変の再開 | 既存認定との一致を確認。新しい試験結果として再認定しない |
| 不合格からの是正 | 原因と変更範囲を記録し必要な試験を再実行。回数上限なし。同じ失敗を根拠なく繰り返さない |

各正式runの前に、trigger（上表のどれか）と対象受入IDを短く記録する。コミットは保存単位であり、コミットのたびに正式認定する必要はない。未認定のsourceを保存する場合はその状態を明示し、未試験codeを正式完了としてmergeしない。

正式run前の準備では、追加/変更classのcoverage対象・collector owner・Test ID/JUnit引数署名・必要XML・分岐0の扱いを、限定試験結果と既存の負canaryで照合する。YKT184/193の既存対策を利用し、同種不整合を全体run後まで持ち越さない。新しい大型collector基盤は作らない。正式run開始から収集までsource/試験/設定/toolsを固定し、必要な変更が生じたらそのrunを混在したまま認定しない。

成功ログ全文の再読、最新概況の多文書一括転記、小部品ごとの全証跡更新を避ける。最新実績は456、依存/次作業は460、本書は運用規則、401は入口リンクに役割を限定する。

## 5. 自走の点検・介入・停止

実行時間・正式試験回数に上限を設けず、初回15ppの固定停止にも戻さない。開始時と意味ある実装/試験区切りで利用枠を確認する。共有枠の観測消費がおおむね10pp進むたびに、次の短い点検を行い、通常はそのまま継続する。

`R到達段階 / D固定IDのclosed・reopened・new / 最後に実測した起動・CHR結果 / 全runのtrigger / 使用率とreset / 次の一手`

1区間で段階も同じ経路の必須条件も進まなければ、その場で依存順と検証単位を修正する。2区間連続（約20pp）で改善がなければ、同じ受入経路の最小再現・停滞理由を限定reviewへ渡し、次の検証仮説を変更する。「次は結線」と再記載するだけの継続をしない。

20ppは自動停止上限ではない。review後は実行可能な是正案か同じ経路の独立必須依存を選び、自走を続ける。PMO介入要の状況・根拠はcheckpointと進捗メッセージへ残すが、別タスクへ勝手に送信しない。PMOの返答を待つだけで止めない。承認・権限・入力が不可欠で、進められる承認済み作業が本当に尽きた場合だけ保存して質問する。

PMOは本チャットで状況確認・停止報告を受けた際に、最新のR/Dと前回点検を比較する。介入対象は2区間の停滞、同種collector障害の再発、理由のない小部品ごとの全正式run、外部仕様の未承認変更、完了根拠の欠落。介入時は次の受入条件・具体的な依存順・検証範囲・担当モデルを修正する指示を作る。品質の不足がある場合は当該成果の認定を保留する。自動監視・別タスクへの自動送信はこの資料作成だけでは設定されない。

残10%以下で新規実装を止め、進行中の必要検証と証跡・差分の保全へ移る。5%付近までに停止する。照会間の消費を見込み保全余力を確保し、不足時は未認定として保存する。reset跨ぎは期間を分け、利用枠の自動reset/追加課金は行わない。

停止は、PG/PTの全完了条件達成、利用枠/実行環境上の継続不能、利用者の停止指示、又は不可欠な外部入力がなく独立作業も尽きた場合。通常の受入単位完了・内部設計の難しさ・依存の大きさだけでは終了しない。PG/PT全完了とIT/ST完了は区別する。

## 6. 再開・報告

意味ある区切りごとに456/460の先頭の現行欄を短く更新する。履歴は保存するが、全checkpoint本文を毎回読み込まない。保存項目はR/D、branch/HEAD、正式run/source、dirty差分、実行中process/run/log、成功/未実行試験、元tree保全hash、未確定契約、次の具体command/確認、枠開始/現在/reset、モデル確認方法。

context中断時は同じ方針で保存地点から再開し、メモリdraftや/tmpだけに頼らない。stashやdirtyを確認せず再適用/消去しない。現行の実装位置・台帳実末尾から採番する。source等不変なら全試験を無理由で再実行しない。

終了報告は「今回受入済み/限定実装/未達」「実起動・CHR証拠」「次のD残条件」「正式run/source・保存commit」「共有枠差と不確実性」「全体見積の根拠」をまとめる。試験数/部品数を完成率へ換算しない。48.3%の見積だけから残週数や費用を確約しない。
