# NG管理・修正・再試験・回帰

## 1. 切り分け

ITの主要調査対象はPG/SSだが、原因は証拠で確定するまで未判定とする。run-template.defectsを使い原失敗のcase/variant/attempt/source/環境/input/actual/expected/barrier/time/raw証跡SHAを固定する。調査中に原入力・oracle・現象を上書きしない。

| 分類 | 確定に必要な証拠 | 変更先 |
|---|---|---|
| PG不備 | 承認SS条件が一意、独立期待と環境が正しく実装の不一致を再現 | 915障害票、916横展開、PG修正・関連PT |
| SS不備 | SSの誤り/不足/矛盾/部品契約欠落を文書/節/条件ID/影響経路で提示 | 914→対象SS→必要PG/PT/IT。仕様だけで解消しない |
| 試験側不備 | 入力/期待値/collector/計測器/手順が設計と異なる証拠 | 原NG保全、試験仕様/tool修正履歴、新attempt。製品不具合と水増ししない |
| 環境不備 | release/config/schema/role/resource/配備hash等の不一致 | 環境是正/差分/再認証。NGを取り消さず原因分類して再試験 |
| 上位設計判断必要 | UI/RDまでの矛盾/承認根拠不足 | 911QA、913UIC、必要912RDF、914相互参照。判断前に期待を選ばない |
| 未判定 | 証拠不足/commit不明/複合原因/決裁待ち | 追加採取/保全/HOLD、原因を推測しない |

915/916の既存IDは実行時の最新台帳末尾から払い出す。今回この作業中の台帳へ新番号を予約・編集しない。設計差分をSSCへ起票する順序はSS362 §8に従う。

## 2. 調査と修正の保全

failure ID→原attempt→BUG/SSC/QA/YKT→修正commit→新release/tool/oracle→再試験attemptの有向リンクを保持する。複数原因は関連票を分ける。未実施/UNKNOWNを失敗率0・合格へ含めない。

期待値を修正する場合は、承認仕様からの誤導出を示す独立表・byte/時刻計算・計測器影響を添付し、reviewerと根拠文書版を記録する。実装に合わせて期待/許容差/試験条件/品質gateを緩めない。BUG2232/2233のsynthetic method/Code長等の計測影響も原失敗と訂正版を分離する。

修正前のsource/archive/環境/原失敗evidenceは読取専用化する。PG/SS修正は今回実施しない。実行後の工程では設計修正を必要承認・上位横断反映後に正本へ反映し、PGPT残件を別管理する。

## 3. 回帰選定

1. 原条件IDと失敗assertionから依存graphを逆引きし、producer/consumer/schema/protocol/owner/状態/権限/file/監視/起動停止の経路を抽出する。
2. 当該case全variant、同経路の正常/異常/境界/競合/再送/復旧/非更新を選ぶ。別endpointでも同codec/transaction/DB grant/lease/file adapter/observerを共有すれば追加する。
3. PTは変更methodだけでなく共有部品とcaller・関連旧不具合/YKT対象を選択し、null/例外/close/型の品質条件を維持する。protocol/DDL/security/common/起動所有の横断変更は451に従う必要全体gate。
4. ITは64layout当該集合、DB/JMS crash、replay/HMAC、owner、file、opsを影響に応じ追加。性能/容量/timeout/再試行変更は同負荷・同環境比較と必要ST/OT再判断を含める。
5. 各caseの選択/非選択理由を修正票へ記録する。「全コードcoverage100」や件数だけで選定しない。

## 4. 再判定

再試験は初回と別attempt/source/環境/時刻/証跡を持つ。当該caseの独立oracle全assertion、影響経路の回帰、必要PT品質、cleanup/復旧、横展開の全対象修正又は非該当根拠が揃うまで閉鎖しない。再試験PASSでも初回FAILは残す。再発は新失敗として原票へリンクしflakyをretry成功で隠さない。
