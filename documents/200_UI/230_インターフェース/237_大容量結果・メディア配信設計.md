# 大容量結果・メディア配信設計

## 1. 目的

MQ上限を超えるlarge-result fileの生成・受渡し・検証・清掃と、audio/video/musicのlocal file配信・Range応答を定める。

関連RD: MQ-019～MQ-020、MQ-039～MQ-041、MSG-F01～MSG-F09、FIL-001～FIL-009、PER-004～PER-006、OPS-013、MON-009。

## 2. File分類

| 分類 | Root | Writer | Reader | Lifecycle |
|---|---|---|---|---|
| Business asset | `asset.root` | 移行・管理作業だけ | API/Web | 永続。定常backup対象外 |
| Large-result transfer | `transfer.root` | API | Web、morning batch | 生成日中保持、次回朝batch全削除 |
| Backup | `backup.root` | morning batch | 運用者/restore | 7世代 |
| Log | `log.root`/journald | 各service | 運用者 | 容量・期間rotation |

各rootは重複させず、symbolic linkで相互配下へ接続しない。DBとMQにはroot基準のrelative pathまたはlogical IDだけを保持する。

## 3. Large-result採用条件

- Web/API業務bodyの上限1,000,000 byteを超える場合。
- 対象interfaceのinline record件数上限を超える場合。
- 初期releaseではSCNRSP01のScenario明細が対象。その他interfaceは上限内page処理を使用する。
- 新規採用時はlayout ID/version、file record layout、最大件数・byte数、画面応答への影響を本設計へ追加する。

## 4. 生成flow

```text
API Application Service
  -> result recordを4,800 byte固定長へencode
  -> transfer.root/yyyyMMdd/<UUID>.part をCREATE_NEW
  -> record順にwrite、flush、fsync
  -> file byte長、record件数、SHA-256を確定
  -> 同一directoryの<UUID>.readyへatomic move
  -> descriptorをMQ responseへ設定
```

- File名はUUIDと固定suffixだけとし、利用者入力を含めない。
- Existing fileを上書きせず、`CREATE_NEW`失敗時は別UUIDを採番する。
- `.part`と`.ready`は同一filesystem上に置き、atomic move非対応なら起動時検証で失敗させる。
- File mode responseを送る前に`.ready`の存在、size、hashを再確認する。

## 5. Descriptor

SCNRSP01の固定dataに次を格納する。

| 項目 | 仕様 |
|---|---|
| Delivery mode | `F` |
| File ID | File名と対応するUUID 36文字 |
| Relative path | `yyyyMMdd/<UUID>.ready`。256 byte以内 |
| File byte長 | `record長 × record件数`、最大48,000,000 byte |
| SHA-256 | Lowercase hex 64文字 |
| Record長 | 4,800 byte |
| Record件数 | 1～10,000 |

File内容にheaderは置かず、同一layoutのrecordだけを連続配置する。改行、BOM、区切文字を挿入しない。

## 6. Web取得検証

Webは次を全て完了してからView Modelとして使用する。

1. Descriptorの必須、型、件数、`byte長 = record長 × 件数`を検証する。
2. Relative pathをnormalizeし、絶対path、`..`、NUL、separatorの表記揺れを拒否する。
3. `toRealPath`後にtransfer root配下の通常fileであることを確認する。
4. File名UUID、`.ready` suffix、descriptor File IDの一致を確認する。
5. 実sizeとdescriptor size、SHA-256を照合する。
6. 4,800 byte境界で終端まで読み、全recordを234のSCNRSP01 recordとして検証する。
7. Record件数、Entry/Audio sequence、重複・順序を検証してView Modelへ変換する。

検証失敗時はfileを使用・削除せず、request ID、File ID、検証stepだけをlogへ記録して503とする。File内容やpath全体をlogへ出さない。

## 7. 削除

- Webは取得成功、失敗、Browser送信完了のいずれでもfileを削除しない。
- APIへの取得完了ACKと第3の業務messageを送らない。
- 次回朝batchが業務アプリ停止中・起動前に、処理開始時点のtransfer root配下にある`.part`と`.ready`を一括削除する。
- 削除対象件数、成功件数、失敗件数、合計byte数を記録する。削除失敗があってもbusiness data削除とは独立して扱う。
- 清掃と同時生成を防ぐため、morning batch中はAPI/Webを停止し、batch lockを取得する。

## 8. Media descriptor配信

```text
Browser GET /.../media/{id} Range?
  -> WebがHTTP session確認
  -> IF-009/012/016でAPIへdescriptor要求
  -> APIがsession/role、logical ID、DB/manifest metadataを検証
  -> Webがasset root、実体、size、MIMEを再検証
  -> HTTP 200/206/416 stream
```

- Descriptorのrelative pathをBrowser URL、HTML、response headerへ出さない。
- `Content-Disposition` file名はdescriptorのsafe file nameをRFC 5987方式でencodeし、CR/LF/quote injectionを防ぐ。
- MIMEは許可list（audio、video/mp4、music container）とfile種別の対応を検証する。任意MIMEを反射しない。
- Path解決後のfileがasset root外、symlinkでroot外、通常fileでない、size不一致なら404または503とし配信しない。

## 9. HTTP Range

| 入力 | 応答 |
|---|---|
| Rangeなし | 200、全長、`Content-Length`、`Accept-Ranges: bytes` |
| 単一valid Range | 206、`Content-Range`、最大1MiB body |
| 複数Range | 最初のRangeだけを採用（現行互換） |
| Suffix Range | File末尾から範囲を算出し最大1MiB |
| 開始がfile長以上/構文不正 | 416、`Content-Range: bytes */<total>` |

Response endは`min(request end, start + 1MiB - 1, file size - 1)`。Media本体をmemoryへ全読込せず、seek可能streamから
buffer 64KiB以下で転送する。Browser切断は正常なclient abortとして記録し、API側dataを変更しない。

## 10. Capacity・監視

| 対象 | 設計上限 | Warning | Critical |
|---|---:|---:|---:|
| Transfer file 1件 | 48MB | 40MB | 48MB超を生成拒否 |
| Transfer root総量 | 5GB | 3.5GB | 4.5GB、生成停止 |
| Transfer file件数 | 10,000 | 5,000 | 9,000 |
| 同時media stream | 20 | 16 | 20超を503/429相当 |

上限は256GB SSDと通常利用5名未満、最大10名を前提とする。SSでfilesystem予約量と実測を確認し、閾値変更は外部設定と
変更記録で管理する。

## 11. Security・integrity

- Asset/transfer rootのOS permissionを最小化し、CaddyとBrowserへ直接公開しない。
- SHA-256は改変検知であり、access認可の代わりにしない。
- Media IDとfile pathを分離し、連番ID推測だけで認可を迂回できない。
- Download、Range、404、416、client abortを監査するが、認証contextと物理pathをlogへ出力しない。
- 移行時の全file manifest検証と定期sampling/full integrity checkを運用化する。

## 12. Traceability

| 設計 | 主なRD |
|---|---|
| File本体をMQへ格納しない | MQ-019、MQ-039、MSG-F01 |
| Descriptor・root検証・hash | MQ-020、MSG-F02～F06、FIL-006～FIL-007 |
| ACKなし・朝batch削除 | MQ-041、MSG-F07～F09、FIL-008～FIL-009、OPS-013 |
| Range・開始性能 | PER-004、PER-006 |
