# 固定長電文共通仕様

## 1. 目的

全Web/API業務電文および内部非同期電文に共通する構造、256 byte header、型、充填、許容値、検証、result codeを定める。

関連RD: MQ-014～MQ-018、MQ-022～MQ-038、MSG-001～MSG-011。

## 2. 電文構造

```text
body = common header 256 byte
     + function fixed data N byte
     + fixed record M byte × record count
```

`256 + fixedDataLength + recordLength × recordCount = totalLength`が必ず成立する。位置は1開始、end位置を含む。
固定dataまたはrecordなしは各長さと件数を0とする。1電文の反復recordは1種類・1領域だけとする。

## 4. 型・充填

| 型 | 表現 | 未設定 | 検証 |
|---|---|---|---|
| X | UTF-8文字列、左寄せ、右ASCII space | 全space | NFC後byte長。後続spaceを除去して復号 |
| N | ASCII `0`～`9`、右寄せ、左ASCII `0` | 原則禁止 | 規定桁、範囲、overflow |
| B | ASCII `0`/`1` 1 byte | Interfaceで許す場合またはerror responseだけspace | 他値禁止 |

- 数値の任意項目はX型で定義し、値を左寄せ、全spaceを未設定とする。
- X型は右space paddingと値末尾のASCII spaceを区別できないため、業務値末尾のASCII spaceを禁止する。検索条件はtrimし、
  Password、質問・回答等の内容項目は末尾spaceをvalidation errorとする。
- CR、LF、TAB、NULを業務項目へ含めない。
- 文字列はNFC正規化後にUTF-8 encodeし、規定長超過時は変換例外。切捨てない。
- UTF-8 multi-byte列を項目境界で分割しない。
- Document、設定、生成fileの改行はLFとする。

## 5. 必須区分

| 記号 | 意味 |
|---|---|
| M | Request/internalでは常に必須。Responseでは成功・冪等成功時必須 |
| C | 条件付き必須。条件を項目表に記載 |
| O | 任意。未設定は全space |
| F | 固定値または予約。送信側が指定値/spaceを設定 |

### 5.1 Result code別response検証

Responseはheaderの処理結果codeを先に検証し、次のprofileでdata/recordを検証する。

| Profile | Result code | Data | Record |
|---|---|---|---|
| 成功 | `0000`、`0200` | M/Fおよび成立するCを通常規則で設定 | Layout定義の件数・必須規則 |
| 業務・system error | 上記以外 | Fは定義値。個別にerror時設定を指定したfield以外はX=全space、N=全0、B=space | 0件 |

- Error fillerは未設定値であり、通常時の最小値やM条件を満たす値とは解釈しない。Receiverはerror profileへ通常data validatorを
  適用してprotocol errorにしてはならない。
- 個別layoutがerror時の最新状態、retry秒、利用者message等を定める場合、そのfieldだけ個別条件を優先し、残りはerror fillerとする。
- Error responseも固定data長と総電文長を変えない。Headerのrecord長はlayout定義値、record件数は`000000`とする。
- `0200`は保存済み成功結果を再構成し、`0000`と同じdata/record必須規則を使用する。

## 6. Message・Correlation ID

- Message IDは送信messageごとに新しいUUIDを採番する。再配送時は変更しない。
- Root requestのCorrelation IDは自身のMessage IDと同じにする。
- ResponseのCorrelation IDは対応requestのMessage IDと同じにする。
- Internal async messageは新しいMessage IDを持つ。`QWKREQ01`のCorrelation IDは元の質問受付request Message ID、
  `WLGEVT01`は対応する業務request Message IDを設定し、対応MQ requestがないHTTP処理ではevent自身のMessage IDとする。
- `NKMessageID` propertyとMessage ID、`JMSCorrelationID`とCorrelation IDを完全一致で照合する。
- Transport再配送は同じMessage IDを維持する。利用者によるtimeout後の再操作は新しいMessage IDでもよいが、更新layoutの
  operation tokenで同一論理操作を判定する。

更新layoutのoperation tokenはowner、layout、target、canonical payloadのHMAC-SHA-256と組み合わせて`request_inbox`へ保存する。
HMAC keyはDB/Gitと分離したsystemd credentialとし、Password等の低entropy値をoffline推測可能な単純hashで保存しない。
同じowner/tokenでHMACが一致すれば保存済み結果を`0200`で返し、layout・target・payloadのいずれかが異なれば`0105`とする。

## 7. Result code

| Code | 分類 | 意味 | Web処理 |
|---|---|---|---|
| `0000` | 成功 | 正常 | 通常表示 |
| `0100` | 入力 | Validation error | 項目error |
| `0101` | 認証 | Login失敗 | 同一認証失敗message |
| `0102` | 認証 | Session無効・期限切れ | Web session破棄、Login |
| `0103` | 認可 | 権限なし | 403 |
| `0104` | 業務 | 対象なし | 404 |
| `0105` | 業務 | 状態・version競合 | 409、再表示 |
| `0106` | 業務 | Lock中 | Retry-After案内 |
| `0107` | 業務 | 取消不可 | 最新状態表示 |
| `0200` | 業務 | 処理済み冪等応答 | 成功相当、保存済み結果使用 |
| `9000` | System | 一時障害 | 503、再操作案内 |
| `9001` | System | Resource/容量上限 | 503、運用警告 |

恒久protocol errorは信頼できるresponseを作成せずDLQ隔離・process終了とするため、result codeを返さない。
Error responseも対応response layoutと5.1のerror profileを使用し、個別定義がある場合だけfield error code/messageを設定する。
Password等をechoしない。

## 8. 受信検証順

1. Bodyが256 byte以上であること。
2. UTF-8として各項目境界をdecodeできること。
3. Protocol、header version、header長、予約領域を検証する。
4. JMS propertyとID/layoutを照合する。
5. Data layout ID/version、要求応答区分、同期区分を検証する。
6. 長さ式、実body長、record件数、interface上限を検証する。
7. 各項目の必須、型、充填、制御文字、許容値、相関を検証する。
8. 利用者起点は認証contextとroleを検証する。Internal eventは認証context全spaceを確認し、接続MQ roleと許可producer/layoutを
   検証してから処理へ渡す。

1～7の不合格は恒久protocol error、8の不合格は認証・認可responseとする。

## 9. Version変更

- 項目位置、長さ、意味、許容値の破壊的変更はData layout versionを上げる。
- 共通header変更はheader versionを上げる。予約領域を用途変更する場合もheader versionを上げる。
- Receiverは明示対応したversionだけを受理し、未知versionを推測して処理しない。
- 同じlayout ID/versionの意味をrelease後に書き換えない。

## 10. Error field共通規則

Error messageを持つresponse dataでは、`error_field` 32 byte、`error_message` 256 byteを末尾に置く。
成功時は両方全space、業務error時だけ設定する。利用者へ表示可能な日本語とし、内部exceptionや秘密値を含めない。
個別layoutがこの2項目を持たない場合、Webはresult codeに対応する共通messageを表示する。
