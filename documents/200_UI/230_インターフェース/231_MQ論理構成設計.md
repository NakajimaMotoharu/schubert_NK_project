# MQ論理構成設計

## 1. 目的

Apache ActiveMQ ArtemisのAddress、Queue、Request/Reply、内部非同期Queue、DLQ、Expiry Queue、security、
再配送および運用境界を定める。

関連RD: MQ-001～MQ-013、MQ-040～MQ-045、FUN-103～FUN-107、ASY-001～ASY-008、MON-005、PER-010。

## 2. Broker構成

- 単一standalone Broker、永続File Journal、persistence有効とする。PostgreSQL JDBC Storeは初期構成で採用しない。
- Acceptorsと管理consoleはloopbackへbindし、internet/LANへ公開しない。
- 業務messageはdurable/persistent、API Consumerはtransacted sessionとmanual ACKを使用する。
- Web/API間はJMS `BytesMessage`、bodyは固定長UTF-8 byte列だけとする。
- Media本体、large-result本体、Java serialized objectをmessageへ格納しない。

## 3. Address・Queue

| Address | Routing | Queue | Producer | Consumer | TTL | 用途 |
|---|---|---|---|---|---|---|
| `nk.sync.request` | ANYCAST | `nk.sync.request.q` | Web | API | 5秒 | 全同期・非同期受付request |
| `nk.sync.reply.web` | ANYCAST | `nk.sync.reply.web.q` | API | Web | 10秒 | Web instance向けresponse |
| `nk.async.work` | ANYCAST | `nk.async.work.q` | API outbox dispatcher | API async worker | なし | 質問等の内部非同期処理 |
| `nk.dead.letter` | ANYCAST | `nk.dead.letter.q` | Broker/Web・API fatal handler | 運用者 | なし | 再配送上限・恒久error隔離 |
| `nk.expiry` | ANYCAST | `nk.expiry.q` | Broker | 運用者 | なし | TTL切れrequest/response保全 |

初期Web instanceは1つとする。将来複数化する場合は`nk.sync.reply.<instance-id>`を追加し、requestのJMSReplyToで
指定する。共通body layoutは変更しない。

## 4. Flow

### 4.1 同期

1. Webが`nk.sync.request.q`へpersistent requestを送る。
2. `JMSReplyTo`へWeb reply Address、`JMSCorrelationID`へ業務Correlation IDを設定する。
3. APIが検証・処理し、指定reply Addressへresponseを送る。
4. Web reply Consumerがselectorまたはin-memory correlation registryで待機requestへ引き渡す。
5. Web timeout後のresponseはexpiryへ移し、別requestへ誤対応させない。

### 4.2 非同期受付

Web/API間はrequest 1通、受付response 1通。APIはDB outbox確定後に`nk.async.work.q`へ内部message 1通を送る。
完了pushは行わず、Browserは通知検索の通常Request/Replyで状態を確認する。

## 5. JMS property

| Property | 型 | 必須 | 仕様 |
|---|---|:---:|---|
| `JMSMessageID` | String | ○ | Provider採番のtransport ID。監査用 |
| `JMSCorrelationID` | String | ○ | 共通header Correlation IDと完全一致 |
| `JMSReplyTo` | Destination | requestのみ | 許可済みreply Addressだけ |
| `JMSExpiration` | long | 同期のみ | request 5秒、response 10秒。内部非同期は0 |
| `JMSDeliveryMode` | int | ○ | PERSISTENT |
| `JMSXDeliveryCount` | int | 受信時 | 再配送判定 |
| `NKMessageID` | String | ○ | 共通header Message IDと完全一致 |
| `NKLayoutID` | String | ○ | 共通header Data layout IDと完全一致 |
| `NKProtocolVersion` | String | ○ | `001` |

Bodyとproperty不一致は恒久protocol errorとする。

## 6. Queue policy・容量

| Queue | Message/容量上限 | 警告 | Address full policy |
|---|---|---|---|
| Sync request | 500件または256MB | 250件/70% | BLOCK |
| Sync reply | 500件または256MB | 250件/70% | BLOCK |
| Async work | 10,000件または1GB | 5,000件/70% | BLOCK |
| DLQ | 10,000件または2GB | 1件以上 | BLOCK＋即時運用警告 |
| Expiry | 10,000件または1GB | 1,000件/70% | BLOCK |

Message最大bodyはWeb/API間1,000,000 byte、内部非同期1,000 byteとする。上限超過結果はlarge-result file方式へ切り替える。
Expiry Queueは調査用に7日保持後、Artemis起動後・API起動前の朝batch MQ保守stepで件数・byte数を記録して削除する。
Artemis停止中にjournal/Queue fileを直接操作しない。DLQは自動削除しない。

## 7. 順序・Consumer

- Sync requestはANYCAST 1 Queue。API Consumer並列数の初期値は4、最大8とする。Request/ReplyはCorrelation IDで対応する。
- Async work Consumerは常に1、priorityなし、FIFOとする。`consumer-window-size=0`相当で過剰prefetchを避ける。
- 同一business keyの更新はDB row lock/optimistic lockで順序を保護する。
- BrokerのFIFOだけに業務整合を依存せず、受付日時・受付連番とDB状態を再検証する。

## 8. 再配送・DLQ

- 一時障害は初回＋最大3回再配送とするため、Artemis `max-delivery-attempts=4`相当を設定する。
- 再配送間隔は1秒、5秒、30秒のbackoffとし、上限後にDLQへrouteする。
- Version不一致、body長不整合、不正UTF-8等の恒久protocol errorは再配送しない。API/Webは対象messageを
  original property付きでDLQへ移し、元messageをACKしたtransactionを確定後、processを非zero終了する。
- DLQ messageにはoriginal Address/Queue、transport ID、業務Message ID、Correlation ID、delivery count、error code、
  検知component、検知日時をpropertyとして付与する。Passwordや本文は追加propertyへ複製しない。

## 9. Expiry

- APIが期限切れrequestを受信した場合、業務処理を開始しない。
- Webが待機終了したresponseを受けても画面へ返さない。
- Expiry件数増加は性能劣化、Web停止、Correlation不整合の兆候として監視する。
- 内部非同期messageにTTLを設定せず、待ち時間だけで消失・ERRORにしない。

## 10. Security role

| MQ role | Send | Consume | Browse/manage |
|---|---|---|---|
| `nk_web` | Sync request、DLQ（受信した恒久errorの隔離だけ） | Web reply | 不可 |
| `nk_api` | Web reply、Async work、DLQ（受信した恒久errorの隔離だけ） | Sync request、Async work | 不可 |
| `nk_mq_maintenance` | 不可 | 不可 | Expiry件数取得と7日超messageのselector purgeだけ |
| `nk_ops` | 原因除去後の承認済み再投入 | 不可 | DLQ/Expiry browse、承認済み個別削除、管理console/API |

Queue作成・削除、security変更は構築roleだけに許可する。Application userはdynamic Queue作成、DLQ purge、management操作不可。
`nk_web`/`nk_api`のDLQ権限は対象Addressへのsendだけであり、browse/consume/purgeを許可しない。
`nk_mq_maintenance` credentialはroot管理のsystemd credentialとし、任意Queue操作やDLQ purgeを許可しない。

## 11. 運用

- ArtemisはPostgreSQL・DB/file朝処理後、API/Web前に起動し、Expiry保守stepを完了してからAPIを起動する。
  停止はWeb、API、Artemisの順。
- Journal、paging、large message、DLQ/Expiry directoryを個別監視する。
- DLQ再処理は原因、対象Message ID、件数、承認者、実行結果を記録する。全件一括再投入をdefaultにしない。
- Broker再起動後、durable Queue件数、Consumer、journal errorなしをreadiness条件とする。
