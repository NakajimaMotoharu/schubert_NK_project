# 処理方式・状態遷移設計

## 1. 目的

同期処理、非同期受付、通知、取消、質問・回答、再配送および再起動時の基本flowと状態遷移を定める。

関連RD: FUN-101～FUN-108、NTF-001～NTF-012、ASY-001～ASY-009、QST-001～QST-105、MQ-002～MQ-010、MQ-040～MQ-045、AVL-004～AVL-005。

## 2. 同期Request/Reply

```text
Browser -> Web Controller
  -> HTTP入力検証
  -> fixed-width request作成
  -> Artemis request Queue
  -> API protocol/session/role検証
  -> inbox重複確認
  -> Application Service / DB transaction / file metadata参照
  -> fixed-width response
  -> Artemis reply Queue
  -> Web response検証・View Model変換
  -> HTML response
```

- 1画面処理は原則、業務request 1通とresponse 1通の計2通とする。
- Webのreply待ちは2秒。Timeout時に同じ操作を自動再送しない。利用者へ再操作可能なerrorを返す。
- 参照処理は再操作しても副作用を持たない。更新処理はMessage IDと業務keyで冪等にする。
- 期限切れrequestをAPIが取得した場合は業務処理せずExpiry Queueへ移す。Commit済みresponseの遅延到着はWebが破棄する。
- APIの業務commit後にACK前で停止した場合、再配送時はinboxの保存済みresponseを返してACKする。

### 2.1 Web HTTP log投影

Webのresponse filterはHTTP status・elapsed確定後、本文・cookie・認証contextを含まない`WLGEVT01`と業務Message IDの対応を
technical schemaの`web_log_outbox`へ登録する。Dispatcherは専用Queueへpersistent送信し、APIは
`app_logs.source_message_id`で冪等にDBへ投影する。これによりLog画面はAPIの業務監査だけでなく、現行相当のWeb REQUEST
（method、path、status、elapsed、remote address）も検索できる。

更新POSTではoperation tokenを結果確定まで保持し、API側でowner＋token＋payload HMACを照合する。同じtokenの再操作は新しい
Message IDでも保存済み結果を返す。Tokenが同じでpayloadが異なる場合は
保存済み成功を返さず競合errorとする。

## 3. 非同期受付

質問要求は次の順序で処理する。

```text
Web -> API QUESTION_SUBMIT request
  -> session/role検証
  -> request_inbox重複確認
  -> DB transaction
       question INSERT
       async_job INSERT (RECEIVED)
       notification INSERT (RECEIVED / ACCEPTED)
       mq_outbox INSERT
  -> commit
  -> outbox dispatcherがinternal Queueへpersistent message送信
  -> send確認・outbox SENT
  -> QUESTION_SUBMIT response（受付ID）
  -> internal ConsumerがFIFOで1件取得
  -> RECEIVEDからPROCESSINGへ条件付き更新
  -> 初期releaseのAnswerProviderが空文字回答を作成
  -> answer INSERT、job/notification COMPLETED
  -> ACK
```

DB commitから内部Queue送信の間に停止した場合は、再起動後にoutbox dispatcherが未送信行を再送する。送信確認後に
受付responseが失われた場合、同じMessage IDで再操作すると既存受付IDを返す。このoutbox/inbox方式をDB更新とMQ送信の
整合方式とし、初期構成でXA transactionを使用しない。

## 4. 内部状態

| 状態code | 利用者表示 | 意味 | 許可操作 |
|---|---|---|---|
| `RECEIVED` | 受付通知 | 永続化済み、処理開始前 | 所有者による取消 |
| `PROCESSING` | 受付通知 | Consumerが処理権を取得済み | 閲覧のみ |
| `COMPLETED` | 処理済通知 | 回答または結果確定 | 通知明細・回答閲覧 |
| `ERROR` | エラー通知 | Workerが確定した業務処理失敗、または最終再配送失敗を整合処理済み | error内容閲覧 |
| `CANCELLED` | 取消済み | 処理開始前に取消確定 | 閲覧のみ、次回朝batch削除 |

```text
RECEIVED ──start──> PROCESSING ──success──> COMPLETED
    │                    └─failure──> ERROR
    └─cancel──> CANCELLED
```

これ以外の遷移は拒否する。`COMPLETED`、`ERROR`、`CANCELLED`は終端状態であり、同じ遷移要求は冪等成功、
異なる遷移要求は業務errorとする。

## 5. 取消flowと競合制御

1. Webは通知明細が`RECEIVED`の場合だけ取消buttonを表示する。
2. APIは認証context、所有者（ADMINでも初期releaseは本人受付の取消だけ）、現在状態を再検証する。
3. `UPDATE ... WHERE state='RECEIVED'`で`CANCELLED`へcompare-and-setする。
4. 更新件数1なら取消成功。0なら最新状態を再読し、既に`CANCELLED`なら冪等成功、その他は取消不可を返す。
5. Queueに残るinternal messageはConsumerが取得し、DB状態`CANCELLED`を確認して業務処理せずACKする。

Consumerの`RECEIVED -> PROCESSING`更新と取消更新は同じ行の条件付き更新で競合させ、先にcommitした処理だけを有効とする。

## 6. 通知lifecycle

- 1件の非同期受付につき1件の通知rowを作り、通知区分と内部状態を遷移させる。状態ごとに別rowを増やさない。
- `RECEIVED`と`PROCESSING`は画面上「受付通知」と表示する。
- `COMPLETED`は「処理済通知」、`ERROR`は「エラー通知」、`CANCELLED`は「取消済み」と表示する。
- 手動削除操作と通知削除電文は設けない。
- `COMPLETED`/`ERROR`は状態遷移から24時間以上経過後、`CANCELLED`は次回朝batchで削除する。
- `RECEIVED`/`PROCESSING`は経過時間だけで削除しない。
- 通知削除時に質問・回答をcascade deleteしない。

## 7. 質問・回答lifecycle

| Event | Question | Answer | Notification |
|---|---|---|---|
| 受付 | active | なし | RECEIVED |
| 初期stub完了 | active | 空文字列、回答日時あり | COMPLETED |
| 取消 | active | なし | CANCELLED |
| 処理error | active | なし | ERROR |
| 利用者削除 | `deleted=true`、削除日時 | 質問と同じ論理削除scope | 通知は変更しない |
| 朝batch物理削除 | 関連通知なし・当日backup成功時だけ削除 | questionと同一transactionで削除 | 事前に削除済み |

論理削除後は通常検索、質問明細、通知経由の本文表示から即時除外する。通知が残っている場合、その明細は
「質問・回答は削除済みです」と表示し、本文を返さない。

## 8. Error・再配送

| 分類 | 例 | 処理 |
|---|---|---|
| 業務error | 入力上限、権限不足、取消不可、対象なし | 正常responseのresult codeで返す。Process継続 |
| 一時system error | DB一時切断、file I/O一時失敗 | rollbackし最大3回再配送。上限時は下記の状態/DLQ整合flow |
| 恒久protocol error | version不一致、長さ不整合、illegal UTF-8 | 再試行せずDLQ、非zero終了、systemd再起動 |
| Reply timeout | Web待ち時間超過 | Webは遅延responseを使用せず再操作案内。API側の結果はinboxで確定 |
| Stub業務error | AnswerProviderの予期した失敗 | job/notificationをERRORへ更新しACK |

DLQからの再処理は運用者が原因を除去し、original Message IDを維持したまま専用手順で通常Queueへ戻す。
重複防止表により既処理messageを再実行しない。

内部workの最終再配送で失敗理由をDBへ記録できる場合は、同一transactionでjob/notificationを`ERROR`へ更新し、original
messageをDLQへ送るoutboxを登録する。DLQ送信確認後に元messageをACKする。DB障害等でこのtransaction自体を確定できず
BrokerがDLQへrouteした場合は、復旧後のDLQ整合手順で受付ID/Job IDとDB状態を照合し、`ERROR`確定または安全な再投入を
選択する。DLQに隔離されたまま利用者状態を無期限に放置しない。

## 9. 再起動時の回復

- Artemis journalが未ACK requestとinternal messageを再配送する。
- API起動時に未送信outboxを走査し、送信を再開する。
- `PROCESSING`のままAPI停止したjobは、対応message再配送時にlease期限ではなく処理所有記録を確認して再開する。
  初期stubは短時間かつ冪等であり、同じ受付IDの回答INSERTを一意制約で重複防止する。
- 業務timeoutを設けず、待ち時間だけでERRORへ遷移しない。
- 将来AI連携時は外部正常/異常通知を受けるまで1件目を`PROCESSING`に保持し、次のmessageを処理しない。

## 10. 監査項目

全flowでHTTP request ID、業務Message ID、Correlation ID、JMS transport ID、認証利用者、受付ID、処理状態、
再配送回数、result code、elapsed timeを関連付ける。Password、認証context ID、質問本文および回答本文はlogへ出力しない。
