# コンポーネント・接続設計

## 1. 目的

Web Java、API Java、Artemis、PostgreSQL、Caddyおよびlocal file間の接続、資格情報、timeout、障害境界を定める。

関連RD: SYS-005～SYS-010、MQ-001～MQ-013、MQ-019～MQ-022、DAT-003、FIL-001～FIL-009、MON-001～MON-006。

## 2. 接続matrix

| From | To | Protocol | 認証 | Timeout/再試行 | 用途 |
|---|---|---|---|---|---|
| Browser | Caddy | HTTPS | form login後のsession cookie | Browser標準 | 画面、media、download |
| Caddy | Web Java | HTTP loopback | 接続元をloopbackへ限定 | connect 2秒、response 30秒。streamはidle 60秒 | reverse proxy |
| Web Java | Artemis | JMS over core protocol | Web専用MQ user | connect 3秒、同期reply待ち2秒 | 全Web/API業務通信 |
| Web Java | PostgreSQL technical schema | JDBC loopback | Web technical専用role | connect 3秒 | HTTP session、失効再試行、Web log outboxだけ |
| API Java | Artemis | JMS over core protocol | API専用MQ user | reconnectはArtemis client設定、再配送最大3回 | request消費、reply、内部非同期 |
| API Java | PostgreSQL | JDBC/TLS不要のloopback | application role | connect 3秒、queryは機能別上限 | 業務data・session・log |
| Migration/batch | PostgreSQL | `psql`/JDBC loopback | 専用role | task単位timeout | schema変更、backup、削除 |
| API Java | business asset root | local filesystem read | OS permission | file I/O errorは業務/system errorへ分類 | metadata照合、descriptor作成 |
| Web Java | business asset root | local filesystem read | OS permission | stream中断を記録 | media本体配信 |
| API Java | transfer root | local filesystem write/read | OS permission | atomic rename | 大容量結果生成 |
| Web Java | transfer root | local filesystem read | OS permission | descriptor検証後だけ読取 | 大容量結果取得 |

同期reply待ち2秒は、通常画面p95 2.5秒のうちCaddy、Web処理、HTML転送の余裕を確保するための初期値である。
業務処理を自動取消するtimeoutではない。reply待ちtimeout後の遅延応答は専用reply Queueのexpiryへ移し、Webは使用しない。

## 3. Network・OS境界

- 外部firewallは55160/tcpだけを許可する。
- CaddyからWeb、Web/APIからArtemis、Web/APIからPostgreSQLはすべてloopback接続とする。
- Web、API、Artemis、PostgreSQL、Caddyは異なるOS service unitとし、可能な範囲で異なるservice accountを使用する。
- business asset rootはWeb/APIにread-only、transfer rootはAPIにwrite、Webにreadを付与する。
- MQ、DB、session、password、backup暗号鍵等の秘密情報はrootまたは各serviceだけが読める外部設定へ置く。

## 4. MQ接続責務

### 4.1 Web側adapter

1. HTTP入力を画面modelで検証する。
2. 認証済み要求ではHTTP sessionから認証context IDを取得する。
3. 機能別DTOを固定長bodyへencodeする。
4. 業務Message IDをJMS property `NKMessageID`へ、業務Correlation IDを`JMSCorrelationID`へ写す。
5. Request Queueへpersistent messageとして送信し、correlation IDに対応するreplyを待つ。
6. header、長さ、JMS property、layout versionを検証してDTOへdecodeする。
7. timeout時は遅延応答を画面へ反映せず、再操作可能なsystem errorを表示する。

JMS providerが採番する`JMSMessageID`はtransport IDとして別途logへ記録する。送信前に確定できる業務Message IDとの
対応は`NKMessageID` propertyで一意に照合する。これによりRDのmessage ID照合要件とJMS providerの採番仕様を両立する。

### 4.2 API側adapter

1. JMS propertyと共通headerを照合する。
2. protocol/layout/byte長/必須/許容値を業務処理前に検証する。
3. 利用者起点要求は認証context IDをhash照合し、session、account有効性、roleを再検証する。
4. Web/API要求はMessage IDを`request_inbox`で確認し、重複時は保存済み結果を返す。内部work/log eventは
   `async_jobs`/`answers`の一意制約または`app_logs.source_message_id`で重複を排除する。
5. Application Serviceを実行し、必要なDB transactionをcommitする。
6. Reply Queueへpersistent responseを送信し、requestをmanual ACKする。

業務処理commit後にreply送信が失敗した場合も、再配送時は保存済み結果を同じcorrelation IDで再送し、更新を重複実行しない。

## 5. DB接続とrole

| Role | 権限 |
|---|---|
| `schubert_web_session` | Web technical schemaのHTTP session、失効再試行、Web log outboxだけのDML。業務schemaはUSAGEも不可 |
| `schubert_app` | API Javaが必要とするschemaのSELECT/INSERT/UPDATE/DELETE。DDL不可 |
| `schubert_migration` | version付きmigrationのDDL/DML。通常運転では使用しない |
| `schubert_batch` | `batch_runs`の記録と業務/technical schemaのallowlist済みmaintenance function実行。その他tableの任意SELECT/DML、ciphertext閲覧不可 |
| `schubert_backup` | `pg_dump -Fc`対象schema/table/sequenceの読取だけ。DML/DDL/SET ROLE、復号key、backup unit外のcredential利用不可 |
| `schubert_ops_ro` | 障害調査用SELECT。account hash、session token hash本文への直接権限は付与しない |

Web Javaは`schubert_web_session`以外のDB roleを使用しない。Connection pool初期上限はWeb session 2、API 8、batch 1とし、
詳細値は負荷試験結果で各上限以下に調整する。

## 6. File接続

- DBとdescriptorには絶対pathを保存・送信しない。
- API Javaは論理IDから許可root配下の相対pathを解決し、`normalize`、実体path、通常file、root配下を検証する。
- Web JavaはAPIの検証を信用して省略せず、同じroot検証を再実施する。
- Symbolic linkを介してroot外へ出るfileは拒否する。
- Transfer fileは`.part`で完全生成し、size/hash確定後に同一filesystem内で`.ready`へatomic renameする。

## 7. 設定分類

| 分類 | 例 | 管理 |
|---|---|---|
| 非秘密・環境依存 | port、Queue名、root path、timeout、監視mode | root所有の外部設定file。雛形だけGit管理 |
| 秘密 | DB/MQ password、session signing secret | service別credential file。Git禁止 |
| Application定数 | header長、layout ID、項目byte長、result code | sourceと本設計を同時version管理 |
| 運用閾値 | disk、Queue、DLQ、log容量 | 外部設定。変更記録を残す |

設定は起動時に相互整合を検証し、必須値欠落、同一Queueの誤設定、root重複、global bindを検知した場合は起動を失敗させる。

## 8. Health・障害境界

| Component | Liveness | Readiness |
|---|---|---|
| Caddy | process active | Web upstreamへ接続可能 |
| Web Java | JVM/HTTP応答 | Artemis接続、reply Consumer、technical session store/log outbox dispatcher、固定長codec初期化完了 |
| Artemis | broker process | journal、Address/Queue、acceptor、disk使用率正常 |
| API Java | JVM/Consumer thread | Artemis、PostgreSQL、必要asset rootに接続可能 |
| PostgreSQL | process/`pg_isready` | migration version一致、read/write probe成功 |
| morning batch | unit終了code | 当日run recordの工程別結果 |

固定長変換・恒久protocol errorは対象messageをDLQへ隔離してからJava processを非zero終了させる。Systemdはrate limit内で
再起動し、同一不正messageを通常Queueへ戻さない。
