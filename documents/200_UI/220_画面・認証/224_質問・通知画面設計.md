# 質問・通知画面設計

## 1. 目的

質問要求、受付完了、通知一覧・明細、受付取消、質問回答検索・閲覧・削除の画面仕様を定める。

関連RD: FUN-010～FUN-013、FUN-101～FUN-108、NTF-001～NTF-012、ASY-005～ASY-009、QST-001～QST-010。

## 2. SCR-018 質問要求

| 項目 | HTTP名 | 必須 | 仕様 |
|---|---|:---:|---|
| 質問 | `question` | ○ | NFC後UTF-8で1～4096 byte。CR/LF/TAB/NULと末尾ASCII space不可 |
| Operation token | hidden | ○ | 36 byte UUID。二重送信防止 |
| CSRF | hidden | ○ | Spring Security token |

質問は幅100%の複数行表示controlを使用するが、初期固定長電文では改行を許可しないため、改行入力時はfield errorとする。
残りbyte数をclient-sideに表示するが、server/APIで必ず再検証する。Password、token等を画面やlogに含めない。

`送信`後、APIが質問・受付通知を永続化し内部Queue送信を確認した場合だけSCR-019へ遷移する。Timeout時は同じ
operation tokenを保持して再送を許可し、既存受付があれば同じ受付IDを返す。

## 3. SCR-019 質問受付完了

表示項目:

- `質問を受け付けました。`
- 受付ID（26文字の公開ID）
- 受付日時（JST `yyyy-MM-dd HH:mm:ss`）
- 質問先頭200文字相当の確認表示（HTML escape）
- `通知を確認`、`続けて質問`、`メニュー`link

Browser refreshで質問を再送しないGET画面とする。受付IDから所有者を推測できないrandom IDを使用する。

## 4. SCR-020 通知一覧

### 4.1 検索条件

| 項目 | 許容値 | 既定 |
|---|---|---|
| 通知区分 | 空/`ACCEPTED`/`COMPLETED`/`ERROR` | 空 |
| 受付日From/To | `yyyy-MM-dd`、From≦To、最大366日 | 空 |
| Page | 1以上 | 1 |

Login本人の通知だけを対象とし、ADMINも他利用者通知へscopeを広げない。並びは状態遷移日時降順、同時はID降順、
50件/pageとする。

### 4.2 一覧項目

| 項目 | 表示 |
|---|---|
| 区分 | 受付通知/処理済通知/エラー通知。PROCESSINGも受付通知 |
| 受付ID | 公開ID |
| 受付日時 | JST秒単位 |
| 最終更新日時 | JST秒単位 |
| 概要 | 質問先頭100文字。論理削除済みは`削除済み` |
| 操作 | `明細`linkのみ。手動削除なし |

## 5. SCR-021 通知明細・取消

| 状態 | 表示 | 操作 |
|---|---|---|
| RECEIVED | 受付ID、受付日時、質問、`受付中` | `処理を取り消す` |
| PROCESSING | 上記、処理開始日時、`処理中` | 閲覧のみ |
| COMPLETED | 質問、回答、回答日時 | 質問回答明細へのlink |
| ERROR | 質問、error code、利用者向けerror内容、発生日時 | 閲覧のみ |
| CANCELLED | 受付ID、取消日時、`取消済み` | 閲覧のみ |

質問・回答が論理削除済みなら本文を返さず`質問・回答は削除済みです。`と表示する。

取消は確認check付きPOSTとし、APIが所有者と`RECEIVED`を再検証する。競合でPROCESSINGへ進んだ場合は取消不可messageと
最新状態を表示する。取消buttonはPROCESSING、COMPLETED、ERROR、CANCELLEDに表示しない。

## 6. SCR-022 質問回答一覧

### 6.1 検索条件

| 項目 | USER | ADMIN | 上限・許容値 |
|---|---|---|---|
| Keyword | ○ | ○ | 質問または回答の部分一致、256 byte |
| 受付日From/To | ○ | ○ | 最大366日 |
| 利用者名 | × | ○ | 完全一致、64 byte |
| 回答状態 | ○ | ○ | 空/`ANSWERED`/`UNANSWERED`/`ERROR` |
| Page | ○ | ○ | 1以上、50件/page |

USERは本人所有だけ、ADMINは全利用者を対象とする。論理削除済みを通常検索へ含めない。並びは受付日時降順、ID降順。

### 6.2 一覧項目・操作

- 受付日時、利用者（ADMINだけ）、質問先頭100文字、回答状態、回答日時、`明細`、`削除`を表示する。
- 一覧削除は対象質問の要約と確認checkを表示するPOSTとし、成功後に一覧へ戻す。
- 取消と削除を混同しない。質問回答削除は処理状態を変更せず、本文を検索・閲覧対象外にする。

## 7. SCR-023 質問回答明細・削除

表示項目は受付ID、所有利用者（ADMINのみ）、質問全文、受付日時、回答全文（空文字は`（空の回答）`）、回答日時、
処理結果とする。USERは本人所有、ADMINは全利用者を閲覧・削除できる。

`質問・回答を削除`は確認check付きPOST。API成功後は一覧へredirectし、同じURLへの再GETは404とする。重複削除は
利用者向けには成功扱いとするが、別利用者のIDを指定した場合は404として存在を開示しない。

## 8. 表示上のdata保護

- 質問・回答はHTML escapeし、link化やMarkdown解釈をしない。
- 検索結果snippetにもscript、HTML、control文字を解釈させない。
- Browser cacheを禁止し、request/response bodyをaccess logへ出力しない。
- Error表示に内部exception、Queue、model名を含めない。

## QA-048・QA-049承認反映：受付確認と再操作（2026-10-03）

業務側DB（APIが管理するquestions/関連業務data）が正である。`schubert_web_session.web_receipt_references`はreceiptIdからquestionIdを解決するためのtechnical locatorだけとし、検証済IF025のreceiptId/questionId/submittedAtの3値以外を保存しない。本文・回答・password・認証context・operation token・owner・結果snapshot・検証済flagを蓄積しない。

SCR019のGETごとにlocatorを読む短Web transactionを終了してからfresh MessageIDのIF030を現在API認証で呼び、API側の現在owner認可に加えてquestionId/receiptId/submittedAtを照合する。日時比較は既存wireのUTC millisecond精度へ揃え、DBの追加microsecondを誤不一致にしない。表示はこの要求で取得したAPI結果だけをHTML escapeし、request scopeへ置く。不一致・他人・削除済み・locator欠落・API確認不能は既存error処理へ進め、古いlocatorやsessionから受付成功/本文を補わない。

IF025成功後のWeb保存は3値をimmutableに登録する。同receiptの同値再登録は冪等、異なる値の競合は上書きせず非成功・診断とする。業務commitとWeb保存は別transactionなので一時欠落が起こり得る。その際、業務受付を取り消したと仮定せず、新operation tokenで質問を再生成しない。保持中の同token/同入力の正規再操作からAPIの既存確定受付結果を取得し、Web参照登録を再試行する。参照欠落のURLだけからquestionIdを推測して復元する保証はしない。

Backup/restore後もWeb値は信頼せず毎GETのAPI検証を省略しない。修復は正規APIの検証済み結果を根拠にWeb参照を合わせる片方向とし、Web参照を正として業務DBを書き換えない。Webから業務schemaへの直接接続/FK/権限は追加しない。cleanupは当日backup gateの下、業務質問が物理削除されたlocatorだけを固定保守functionで削除し、存続する質問のlocatorへ独自TTLを設定しない。実装・DDL適用・独立PTは未完了であり、QA048承認による設計条件である。

同HTTP session内の全用途を合計してpending＋consumedを最大10件とする。用途/UUID/issuedAtは不変で、completedAt欠落はpending、検証済0000/0200を初めて確認した時刻だけを完成印として保存する。完成印を業務結果・認可・API成功proofの代用としない。入力本文・password・payload/HMAC対応入力・業務result snapshotをsessionへ保存しない。

保持中の同token/同入力POSTは現在API認証と既存owner/layout/target/payload HMAC・保存済み結果の検証を経て再操作する。結果GETのrefreshではAPI更新再送を行わない。新formで枠が必要になった場合だけcompletedAtが最古のconsumedを1件退役し、同時刻は保存list順で決定する。pendingを退役しない。全10件pendingなら新form発行を拒否する。退役済み/不在tokenのPOSTは409と明示再GETを要求し、API送信・新UUID発行・自動再操作は0とする。

8時間idleのsession上限、API Inbox7日の保持起点、wire/HMAC/DDL/Current baselineは変更しない。完成時刻から8時間/7日を新たに延長する保証も追加しない。実装・独立PT・nativeの完成認定は別に行う。
