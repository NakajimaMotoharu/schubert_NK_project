# 現行機能画面設計

## 1. 目的

現行から移行するMenu、検索、scenario閲覧、audio、animation、musicの入力・表示・操作・順序を定める。

関連RD: SCP-001、FUN-002～FUN-007、SYS-006～SYS-007、PER-003～PER-006、TST-001～TST-005。

## 2. SCR-002 Menu

2列card layoutに次を表示する。USERは7項目、ADMINはこれにLog照会とUser管理を加える。

1. Scenario閲覧
2. 検索
3. Animation視聴
4. Music
5. 質問する
6. 通知
7. 質問回答

各cardはtitle、1行説明、遷移先を持つ。Headerに`schubert NK`、login username、role、Logoutを表示する。

## 3. SCR-003 Scenario検索

### 3.1 入力

| 表示名 | HTTP名 | 必須 | 上限・許容値 | 検索 |
|---|---|:---:|---|---|
| 本文 | `q` | 否 | 256 byte | 小文字化検索列の部分一致 |
| Game | `game` | 否 | 空/`NUKITASHI1`/`NUKITASHI2` | 完全一致 |
| Speaker | `speaker` | 否 | API候補、128 byte | 完全一致 |
| 章title | `chapter` | 否 | 256 byte | 大文字小文字を区別しない部分一致 |
| 形態 | `entry_type` | 否 | 空/`dialogue`/`narration` | 完全一致 |
| 音声 | `voice` | 否 | 空/`with`/`without` | boolean一致 |
| Page | `page` | 否 | 1～999999、default 1 | 100件単位 |

Game変更時はsame-originの外部JavaScriptでformをsubmitし、Speaker候補を対象gameで再取得する。Inline event handlerはCSPで
許可しない。JavaScript無効時も検索buttonで同じ処理を実行できる。全条件はAND。文字列はtrimする。

### 3.2 表示・順序

- 結果は現行`script_entries.id`から移行時に固定する`script_entries.display_order`昇順、1 page 100件。
- Game、章、形態label、speaker、scenario path/line、audio path、本文を表示する。
- Scenario `開く`は対象entry anchorへ遷移する。
- Audioがある場合だけinline playerとDLを表示する。
- Speaker候補は対象game内の出現数降順、同数は名前昇順。

## 4. SCR-004～007 Scenario階層閲覧

### 4.1 Game・Route・File

- Gameは`display_order`、Routeは2桁prefix昇順、Fileはgame表示順・`script_files.display_order`昇順。
- Route名称は現行固定mapを維持し、map外は`未分類`。
- File cardの表示titleは章title、section code、file名の順で最初の非空値とし、game、display path、entry件数を表示する。

### 4.2 Scenario本文

- Headerに表示title、game/display path、上位linkを表示する。
- 前後navigationを本文の上と下に置く。全gameを`games.display_order, script_files.display_order`で並べた前後とする。
- Entryは`entry_index, display_order`順。line番号、speaker（ある場合）、本文、audio（ある場合）を表示する。
- 直接anchor遷移したentryは現行同様highlightする。
- 複数voice linkが存在した場合は同じentry内に全playerを表示し、entry本文を重複表示しない。これは現行DBの将来整合を改善する設計である。

## 5. Audio endpoint

| URL | 応答 |
|---|---|
| GET `/audio/{id}` | `audio/ogg`相当、`Content-Disposition: inline` |
| GET `/audio/{id}/download` | `application/octet-stream`、UTF-8 file名のattachment |

APIからmedia descriptorを取得後、Webが許可root配下を再検証してstreamする。無効ID、root外、欠落fileは404。
Audio playerの操作性は現行を維持し、Range対応可能な実装とする。

## 7. SCR-011～013 Music

- Category順は`曲`、`BGM`、その他名称昇順とする。Section順は`ゲーム`、`アニメ`、`キャラクターソング`、
  その他名称昇順とし、section、trackへ階層遷移する。
- 非`曲`のTrack cardはtitle、display path、MB、player、DLを表示する。`曲`のpair行は現行同様、pair title、Main/Instrumental
  player、DL、欠落placeholderだけを表示し、個別path/MBは表示しない。
- `BGM`等の非`曲`trackはdisplay pathのUnicode code point昇順を移行時`display_order`へ固定する。
- `曲`は次の現行pair規則を移行時に実行し、`pair_key`、`pair_role`、`display_order`へ結果を固定する。画面要求時に
  file systemを再走査・再推測しない。
  1. Titleに`inst`または`instrument`を大文字小文字無視で含むtrackをInstrumental、その他をMainとする。
  2. 先頭の`数字-数字`、Instrumental注記、空白・全角空白・underscore・括弧・句読点・`! + ^ -`を除去し、
     小文字化した値をpair keyとする。
  3. Mainと同一keyを優先する。同一keyがなければ未使用InstrumentalとのLevenshtein距離が2以下の最小値を採用し、
     同距離はdisplay path昇順の先頭を採用する。
  4. Mainをdisplay path昇順で表示した後、未対応Instrumentalをdisplay path昇順で表示する。片方がない場合は
     `メインなし`または`インストなし`を明示する。
- 現行129 fileのdisplay path、byte size、SHA-256、pair結果、表示順を移行manifestの受入基準とする。

Game選択cardのmaster値は次を移行基準とする。

| Code | Title | Display order |
|---|---|---:|
| `NUKITASHI1` | `NUKITASHI` | 1 |
| `NUKITASHI2` | `NUKITASHI2` | 2 |

## 8. Media Range

- Video/musicはRangeなしで200と全長、単一Rangeで206を返す。
- 複数Rangeは最初のRangeだけを採用する現行挙動を維持する。
- 1回のresponse bodyは要求end、file末尾、開始+1MiB-1の最小までとする。
- `Accept-Ranges: bytes`、`Content-Range`、正しい`Content-Length`を返す。
- 無効Rangeは416とし、file総長を`Content-Range: bytes */total`で返す。

## 9. Characterization観点

検索条件、候補順、結果順、page丸め、Route名、章title欠落時のsection code表示、前後file、entry順、audio有無、animation main/SUBTRACK対、
music pair、Range 1MiB上限、download file名を現行との比較対象とする。内部SQL、class、DB IDの一致は要求しない。
