# 認証・認可・セッション設計

## 1. 目的

Login、Logout、account、USER/ADMIN、HTTP session、認証context ID、lockおよびWeb/API二重認可を定める。

関連RD: FUN-001、FUN-009、AUT-001～AUT-004、MQ-004、MQ-021、MQ-036、MON-004、SCP-102。
関連QA/RDF/UIC: QA-044、RDFなし、UIC-004。

## 2. 認証構成

```text
Browser POST /login + CSRF
  -> Web Java Login Controller
  -> LOGIN fixed-width request（username/password/client address）
  -> Artemis
  -> API Java Authentication Service
       account active/lock/password hash確認
       auth_session作成、認証context ID発行
  <- LOGIN response（username、role、context ID、expiry）
  -> Web JavaがHTTP sessionを新規作成
  -> BrowserへSecure/HttpOnly/SameSite cookie
```

Web Javaはpassword照合、account正本およびrole決定を行わない。API JavaがPostgreSQLで認証し、監査logとsessionを確定する。

### 2.1 SCR-001 Login表示

QA-045/UIC-005承認: NKの可視brandは`schubert NK`、document titleは`schubert NK - ログイン`とする。Current titleとの差はUI264 DIF-001/CHR-A01で比較し、認証・error文言・form契約を変更しない。

| 項目 | 仕様 |
|---|---|
| Username | `autofocus`、`autocomplete=username`、最大64 UTF-8 byte |
| Password | `autocomplete=current-password`、最大256 UTF-8 byte。再表示時は常に空 |
| Submit | `ログイン`。CSRF必須、二重押下を抑止 |
| `?logout` | `ログアウトしました。`をsuccess表示 |
| `?error` | User不存在/password不一致/disabledを区別しない認証失敗message |
| `?locked` | Currentと同じ固定文「ログイン試行回数が上限に達しました。15分ほど待ってから再度お試しください。」。実残秒数を画面へ追加しない |

QA-055/UIC-012（2026-11-06利用者承認）: lock時の可視文言は上記固定文を維持する。実際の待機秒数はAPI確定値0～900を従来どおりHTTP `Retry-After`に返す（SS314 §5.2）。固定文は残時間の実測値ではない。Webによる残時間の再計算・URLや画面への動的残秒追加を行わず、302 `/login?locked`、既存error/logout、DIF-001のtitle以外の比較条件を維持する。RD変更・新規DIFはない。

Login前に保存する遷移先はsame-originの安全なGETだけとし、Login成功後に戻す。更新request、外部URL、scheme相対URLは保存しない。

## 3. Account

- UsernameはNFC・trim後の比較用小文字を別列に保持し、大文字小文字を区別せず一意とする。
- PasswordはSpring Security `DelegatingPasswordEncoder`形式のone-way hashだけを保存する。平文と可逆暗号を保存しない。
- Hash algorithmとwork factorはSS工程で採用時推奨値を記録し、Login成功時のrehashを可能にする。
- Roleは`USER`または`ADMIN`の1つ。Account状態は`ACTIVE`/`DISABLED`。
- 現行accountは移行せず、切替前に初期ADMINと必要Userを新規作成する。

## 4. Login入力・失敗制御

| 項目 | 仕様 |
|---|---|
| Username | 1～64 UTF-8 byte、trim、NFC |
| Password | 1～256 UTF-8 byteで電送。作成時policyは12～128文字 |
| User閾値 | 15分窓で5回失敗後、15分lock |
| IP閾値 | 15分窓で10回失敗後、15分lock |
| 成功時 | 該当user/IPの失敗counterをclear |
| 表示 | 不存在、password不一致、disabledを同一messageにする。Lockだけ待ち時間を表示 |

Client addressはCaddyが上書きした信頼済みproxy headerからWebが取得し、Login電文へ設定する。任意の外部
`X-Forwarded-For`を直接信用しない。失敗counterとlock終了はDBへ保存し、API再起動で解除しない。

## 5. 認証context ID

- Cryptographically secure random 32 byteをlowercase hex 64文字で表現する。
- APIはraw IDをLogin responseで返す。通常照合はDBのSHA-256 hashだけを使用し、同一Message IDのLogin responseを冪等再送する
  ために限り、raw IDを外部keyによるAES-GCM暗号文でも保存する。平文では保存しない。
- Webはraw IDをserver-side HTTP sessionの暗号文にだけ保持し、Browser cookieやHTMLへ出さない。
- 利用者起点MQ requestの共通headerへ毎回設定する。APIはhash、expiry、account active、roleを毎回検証する。
- Session固定対策としてLogin成功時にHTTP session IDを変更する。

## 6. Session lifecycle

| 項目 | 初期値 |
|---|---|
| Idle timeout | 8時間（現行維持） |
| 同一account同時session | NKは最大2。3件目Login時は最古を失効 |
| Cookie | Secure、HttpOnly、SameSite=Lax、Path=/。認証情報本体を含めない |
| Logout | API session revoke成功後、Web session invalidate。API障害時もWeb sessionを破棄し、revoke再試行を監査 |
| Password reset | 対象accountの全sessionを即時失効 |
| 無効化/role変更 | 対象accountの全sessionを即時失効し、次回Loginから新roleを反映 |
| 計画再起動 | DB sessionを保持。Web session store回復後に継続可能とする |

HTTP sessionはWeb process memoryだけに置かず、PostgreSQLの専用technical schemaへ永続化する。Cookieのrandom session IDは
DBでhash照合し、allowlist化した`username`、`role`、認証context ID、login日時、CSRF token、安全なSavedRequest、
更新のoperation tokenを用途・UUID・発行日時・任意の初回完成時刻とともに外部keyによるAES-GCM暗号文とする。同session全用途でpending＋consumed合計最大10件を保持する（QA-049、下記承認反映節）。
SavedRequestはsame-origin GETのpath/query（合計2,048 byte以内）だけで、header/bodyを保存しない。Operation tokenに入力本文・
password・固定長bodyを関連付けて保存しない。
Web用DB roleはこのschema以外のUSAGE/表権限を持たず、業務DBを直接参照しない。

Characterization Testでは、現行の`maximumSessions(2)`設定が実効せず、3件のsessionがすべて継続できることを確認した。これは現行の既知不具合`DIF-016`とし、NKの機能仕様には引き継がない。NKはAPI側のsession発行transactionで同一accountの有効sessionをlockし、最大2件と最古revokeを必ず強制する。

Login成功時のsession fixation対策では新session ID/rowを作成してallowlist属性と新CSRF tokenだけを移し、旧rowを同一transactionで
失効する。Web再起動後もCookieとAPI sessionの両方が有効なら継続し、片方が不整合または属性復号/型検証失敗ならLoginへ戻す。

## 7. 認可matrix

| API操作 | USER | ADMIN | 所有者検証 |
|---|:---:|:---:|---|
| Scenario/media/music/animation | ○ | ○ | 不要 |
| 質問送信、本人通知閲覧・取消 | ○ | ○ | 常に本人 |
| 質問回答検索・閲覧・削除 | 本人のみ | 全利用者 | APIでIDごとに検証 |
| Log検索 | × | ○ | Role |
| User一覧・作成・変更 | × | ○ | Role＋自己保護 |

Webはmenu、button、URL handlerでroleを検証し、APIは共通認証filterとApplication Serviceで再検証する。固定長電文の
role値をclientから受け取って信用せず、認証contextからDB上の最新roleを取得する。

## 8. CSRF・session攻撃対策

- 全更新HTTP methodはPOSTとし、Spring Security CSRF tokenを必須にする。
- Login POSTにもCSRFを適用する。
- Session cookieをURLへ含めず、refererやlogへ出力しない。
- CSP、frame拒否、SameSite、Secure、HttpOnlyを併用する。
- Authentication success/failure/lock/block/logout/session revokeをSECURITY logへ記録する。

## 9. 障害時

- Login API timeoutは認証失敗扱いにせず503とし、失敗回数を増やさない。
- 認証context検証のDB障害はdeny closedとし、業務処理を実行しない。
- APIでsession失効を検知したresponseを受けたWebはHTTP sessionを破棄しLoginへ戻す。
- Broker/API停止中のLogoutはWeb sessionを直ちに破棄し、暗号化contextをtechnical schemaの失効再試行rowへ退避する。Web recovery
  taskがIF-002を再送し、検証済0000/0200の確定失効応答だけでrowを削除する。期限未確認はNULLとし、初回Login期限/requested_at+8hで推測しない。一般0102・期限経過・不明・復号不能だけでは削除せず保持・警告する。初期5秒/30秒/5分後は15分間隔で継続し、100回飽和は打切りにしない。IT/ST性能試験で問題があれば間隔を変更して再試験する（QA-050）。有限自動解消は保証せず正規復旧/運用確認へ引継ぐ。Raw contextをlogや平文tableへ出さない。

## 10. 監査・秘密情報

Security logはactor username、結果、remote address、user agent要約、request ID、失敗理由codeを記録する。
Password、password hash、認証context raw/hash、CSRF token、session cookieを記録しない。Username不存在とpassword不一致は
利用者画面では区別しないが、権限を制限した内部reason codeで運用調査可能にする。

API認証context暗号keyとWeb HTTP session暗号keyは分離し、Git・DB・logへ格納しない。Systemd credentialから各processへ渡し、
旧keyで復号可能なrotation期間を設ける。復号失敗はdeny closedとし、対象sessionを失効させる。

## QA-049承認反映：完成状態と容量管理（2026-10-03）

同HTTP session内の全用途を合計してpending＋consumedを最大10件とする。用途/UUID/issuedAtは不変で、completedAt欠落はpending、検証済0000/0200を初めて確認した時刻だけを完成印として保存する。完成印を業務結果・認可・API成功proofの代用としない。入力本文・password・payload/HMAC対応入力・業務result snapshotをsessionへ保存しない。

保持中の同token/同入力POSTは現在API認証と既存owner/layout/target/payload HMAC・保存済み結果の検証を経て再操作する。結果GETのrefreshではAPI更新再送を行わない。新formで枠が必要になった場合だけcompletedAtが最古のconsumedを1件退役し、同時刻は保存list順で決定する。pendingを退役しない。全10件pendingなら新form発行を拒否する。退役済み/不在tokenのPOSTは409と明示再GETを要求し、API送信・新UUID発行・自動再操作は0とする。

8時間idleのsession上限、API Inbox7日の保持起点、wire/HMAC/DDL/Current baselineは変更しない。完成時刻から8時間/7日を新たに延長する保証も追加しない。実装・独立PT・nativeの完成認定は別に行う。
