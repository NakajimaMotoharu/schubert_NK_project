# 管理・ログ画面設計

## 1. 目的

ADMIN用のUser管理とLog照会の入力、表示、更新、権限制御および監査を定める。

関連RD: FUN-008～FUN-009、AUT-002～AUT-003、DAT-003、MON-003～MON-004。

## 2. SCR-014 Log検索

現行layout、100件page、新着順を維持し、accessだけをADMINへ限定する。

| 表示名 | HTTP名 | 上限・許容値 | 条件 |
|---|---|---|---|
| Message | `q` | 256 byte | message/detailsの部分一致 |
| 種別 | `log_type` | 空/ACTION/REQUEST/SECURITY/MQ/SYSTEM/BATCH | 完全一致 |
| Action | `action` | 64 byte | 完全一致 |
| Path | `path` | 256 byte | 部分一致 |
| Level | `level` | 空/INFO/WARN/ERROR | 完全一致 |
| From/To | `from`,`to` | 最大31日 | logged_at範囲 |
| Page | `page` | 1以上 | 100件/page |

一覧は発生日時、種別、level、action、message、request ID、message/correlation ID、HTTP method/path/status/elapsed、
remote addressを表示し、detailsを折りたたむ。APIがtransaction内で記録する業務・security監査と、Webのtechnical outboxから
`WLGEVT01`で投影されたREQUEST logを同じ`app_logs`から検索する。投影遅延中でもWeb local JSONを正本証跡として保持し、
再送後はevent Message IDで二重登録しない。Password、認証context ID、DB/MQ秘密値、質問・回答本文を表示・保存しない。

## 3. SCR-015 User一覧

### 3.1 検索条件

| 項目 | 許容値 |
|---|---|
| Username | 64 byte、前方一致 |
| Role | 空/USER/ADMIN |
| 状態 | 空/ACTIVE/DISABLED/LOCKED |
| Page | 1以上、50件/page |

並びはusername昇順。表示はusername、role、active/disabled、lock終了日時、最終Login日時、作成日時、更新日時、`詳細`。
Password hash、失敗回数のIP別明細、session tokenは表示しない。

## 4. SCR-016 User追加

| 項目 | 必須 | 仕様 |
|---|:---:|---|
| Username | ○ | NFC、trim後1～64 byte、英数字と`._-`、大文字小文字を区別しない一意性 |
| 初期Password | ○ | NFC後12～128文字かつ256 byte以下、usernameと同一不可 |
| Password確認 | ○ | 初期Passwordと完全一致。電文へ重複送信せずWebで照合 |
| Role | ○ | USER/ADMIN。default USER |
| 有効 | ○ | default true |

Password policyは長さを主とし、文字種組合せを強制しない。Common password照合はSS工程でoffline listの採用可否を決める。
作成成功後はSCR-017へredirectする。Username重複はfield error。Passwordをlog、flash、URLへ出力しない。
Formは36文字UUIDのoperation tokenをhiddenで持ち、timeout再表示では同じtoken、成功後は新しいtokenを使用する。

## 5. SCR-017 User詳細・変更

表示項目は一覧項目に加え、lock理由、active session数、最終Password変更日時、作成/更新actorとする。

操作:

| 操作 | 入力 | 制約 |
|---|---|---|
| 有効化/無効化 | 確認check | 自分自身の無効化禁止 |
| Role変更 | USER/ADMIN | 自分自身のADMIN解除禁止。ADMIN 0人化禁止 |
| Password reset | 新Password/確認 | policy再検証。全sessionを失効 |
| Lock解除 | 確認check | lock中だけ表示。失敗counterもclear |

同時更新は`version`によるoptimistic lockを使用し、競合時は409と最新情報を表示する。対象Userに対する全操作を
actor ADMIN、target ID、変更前後（password除外）、request IDとともに監査logへ記録する。
有効/無効、role変更、password reset、lock解除の各POSTはoperation tokenをhiddenで持つ。同じtoken・同じ入力の再操作は
保存済み結果を返し、同じtokenで対象・version・変更値が異なる場合は409として新tokenでの再操作を求める。

## 6. 自己保護・最後のADMIN

- Login中ADMINは自分のaccountを無効化できない。
- 自分のroleをUSERへ変更できない。
- DB constraint/service checkでactive ADMINが0人になる更新を拒否する。
- Password resetは自分自身にも可能だが、更新成功後に現在を含む全sessionを失効してLoginへ戻す。
- これらはUIのbutton非表示だけでなくAPI transaction内で検証する。

## 7. Error・監査

Userが不存在またはUSERが直接URLを指定した場合、対象存在を推測させない。ADMINによる不存在は404、USERは403とする。
DB/MQ一時障害では入力Passwordを再表示せず再入力を求める。監査log保存失敗時はUser更新をcommitせずsystem errorとする。
