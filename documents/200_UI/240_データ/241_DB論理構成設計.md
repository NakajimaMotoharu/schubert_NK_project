# DB論理構成設計

## 1. 目的

PostgreSQL上のschema、entity、関連、data ownership、transaction、論理削除およびmigration方針を定める。

関連RD: DAT-001～DAT-011、FUN-008～FUN-013、ASY-001～ASY-009、BAK-001～BAK-008、MIG-DAT-001～MIG-DAT-008。

## 2. Database・schema

| 項目 | 設計 |
|---|---|
| DBMS | PostgreSQL 18系、構築時点の最新minor |
| Database | `schubert_nk` |
| 文字code/timezone | UTF-8、DB保存は`timestamptz`、画面・電文はAsia/Tokyo |
| 業務schema | `schubert` |
| Web technical session schema | `schubert_web_session`。Web role専用、`schubert`への権限なし |
| Migration schema | `schubert_meta`（schema history） |
| Extension | `pg_trgm`。本文・log部分一致 |
| ID | 内部PKは原則`bigint generated by default as identity`。公開IDはrandom text/UUID |

物理table名・column名はsnake_case。Java側の日時は`Instant`/`OffsetDateTime`とし、文字列日時をDB正本にしない。

## 3. Entity関連

```text
app_users 1 ── N auth_sessions
    │ 1
    ├── N questions 1 ── 0..1 answers
    │                 ├── 1 async_jobs 1 ── 1 notifications
    │                 └── N request references
    └── N audit actor references

games 1 ── N script_files 1 ── N script_entries N ── 0..1 speakers
  │               │                   │
  └── N audio_files └───────────────── N entry_audio_links N ── 1 audio_files

media_assets（video/music metadata、self parent relation）
app_logs（業務entityとFKなし）
request_inbox（Message IDの冪等性・response replay）
mq_outbox（DB commit後のinternal Queue送信）
login_ip_attempts（IP別Login失敗制御）
web_http_sessions / pending_context_revocations / web_log_outbox / web_receipt_references（Web technical schema、業務entityとFKなし）
```

## 4. Data分類・正本

| 分類 | 主table | 更新者 | Backup |
|---|---|---|---|
| Account/session | app_users、auth_sessions、login_ip_attempts | API/ADMIN | 対象 |
| Web technical data | schubert_web_session.web_http_sessions、pending_context_revocations、web_log_outbox、web_receipt_references | Web | 対象。期限切れ/SENT等は既定技術cleanup。受付参照は業務質問の物理削除後だけ |
| Scenario master metadata | games、script_files、speakers、script_entries、audio_files、entry_audio_links | Migration | 再生成可能だがDB整合用にbackup可 |
| Video/music metadata | media_assets | Migration | 再生成可能 |
| 質問・回答・通知 | questions、answers、async_jobs、notifications | API/batch | 対象 |
| Message整合 | request_inbox、mq_outbox | API | 対象 |
| Log | app_logs | API/batch。Web HTTP logはlocal JSON/journald | 対象。ただし現行logは非移行 |
| Material本体 | Local filesystem | 移行作業 | 定常backup対象外、別正本から復元 |

Web Javaは専用roleで`schubert_web_session`の上記4 technical tableだけへ接続し、`schubert`配下の業務tableへ接続しない。受付参照は業務DBを正としたAPI再検証が必要であり、Web値で業務結果/権限を確定しない（QA-048）。

## 5. Transaction境界

| 処理 | 同一transactionで確定するもの |
|---|---|
| User作成・変更 | app_users、session revoke、SECURITY/ACTION audit、request_inbox |
| 質問受付 | questions、async_jobs、notifications、mq_outbox、request_inbox |
| 非同期処理開始 | async_jobsの条件付き状態更新 |
| 空回答完了 | answers、async_jobs、notifications、内部Message ID/Answer一意制約 |
| 受付取消 | async_jobs、notifications、audit |
| 質問回答論理削除 | questions、answersのflag/日時、audit |
| 朝の物理削除 | 対象通知、質問、回答を対象単位で整合順に削除しbatch結果を記録 |
| Web HTTP log採取 | technical schemaのweb_log_outbox登録。API取込時はapp_logsのevent Message ID一意性で確定 |

DB transactionとJMS sendはXAを使わずoutbox/inboxで整合させる。Outbox rowのcommitを先に行い、送信確認後にSENTへ更新する。

## 6. 冪等性

- `request_inbox.message_id`をPKとし、同じMessage IDの再配送を検出する。
- 更新系は`operation_token`にも利用者scope付き一意制約を設け、Browserの再送を検出する。Owner、layout、target、canonical
  payloadのHMAC-SHA-256を保存し、同じtokenでpayloadが異なる場合は競合として拒否する。
- 保存済みresult referenceから同じ業務結果を再構成する。Fixed response byteを保存する場合はlayout/versionを併記する。
- Login contextのreplayに必要なraw tokenは平文保存せず、外部keyによるAES-GCM暗号文とhashをauth_sessionsへ保存する。
- Web HTTP sessionのcookie IDはhash、session attributeは別の外部keyによるAES-GCM暗号文で保存する。
- `mq_outbox.message_id`を一意とし、dispatcher再起動時の二重sendをArtemis duplicate detectionとConsumer冪等性で防ぐ。
- `web_log_outbox.message_id`と`app_logs.source_message_id`を一意とし、Web log再送をDBで重複排除する。

## 7. 論理削除・物理削除

- Questionsとanswersの両方に`is_deleted`、`deleted_at`を持たせ、同一transactionで設定する。
- 通常queryはRepository共通条件で`is_deleted=false`を必須にする。個別SQLの任意判断にしない。
- Notificationが残る間、question/answer本文をresponseへ返さず削除済み表示とする。
- Notificationは論理削除せず、lifecycleに従って朝batchで物理削除する。
- Question/answerの物理削除は当日backup成功、論理削除済み、関連notification不存在を全て満たす場合だけ。
- App userは削除せずDISABLEDとする。監査・所有関係を保持する。

## 8. FK・削除原則

| Parent -> Child | ON DELETE | 理由 |
|---|---|---|
| app_users -> questions/sessions | RESTRICT | Accountを物理削除しない |
| questions -> answers/async_jobs | CASCADE | 最終物理削除を同一aggregateで実施 |
| questions -> notifications | RESTRICT | Notification削除前の本文物理削除防止 |
| async_jobs -> notifications | RESTRICT | 状態追跡を保護 |
| games -> master tables | RESTRICT/CASCADEを現行同等に個別指定 | 誤master削除防止 |
| script_entries -> entry_audio_links | CASCADE | Entry再構築時のlink整合 |
| audio_files -> entry_audio_links | RESTRICT | 参照中audio削除防止 |

## 9. Index方針

- FK column、所有者＋日時、状態＋遷移日時、論理削除flag＋削除日時にbtree indexを設ける。
- Scenario本文・章、Log message/details、質問/回答keywordへ必要なGIN/pg_trgm indexを設ける。
- USER question検索は`(owner_user_id, is_deleted, submitted_at desc, id desc)`、ADMIN検索は
  `(is_deleted, submitted_at desc, id desc)`を分ける。
- Notification cleanupは`(state, state_changed_at)`、question物理削除は`(is_deleted, deleted_at)`を使用する。
- Indexは実query planと現行99,661 entry、最大同時10名でPT/IT確認する。

## 10. Migration

- Flyway等のversion付きmigrationを使用し、初回DDL単独に依存しない。
- Migrationはforward-onlyを原則とし、release切戻しに必要な互換期間は旧applicationが読めるschema変更順を設計する。
- Migration前にDB backup、schema version、app versionを記録する。
- Master投入はstaging tableへload、件数/hash/constraint検証後にtransactional swapまたは短時間切替する。
- Application起動時にDDLを自動補完しない。期待migration version不一致はreadiness falseとする。

## 11. Data validation

- 文字項目のNFC・byte上限はAPI/Migrationで検証し、主要code/state/roleはDB CHECKでも保護する。
- Username、receipt ID、operation token、message ID、media logical IDへ一意制約を設ける。
- Question本文は1～4096 octet、answerは0～4096 octet。Control文字と末尾ASCII spaceをapplicationで拒否する。
- Storage relative pathへ絶対pathを保存しない。Migration時にroot外解決、file欠落、size/hash不一致を拒否する。
  Display pathはsanitized表示専用であり、file解決へ使用しない。

## QA-048承認反映：受付参照の正本・整合性（2026-10-03）

業務側DB（APIが管理するquestions/関連業務data）が正である。`schubert_web_session.web_receipt_references`はreceiptIdからquestionIdを解決するためのtechnical locatorだけとし、検証済IF025のreceiptId/questionId/submittedAtの3値以外を保存しない。本文・回答・password・認証context・operation token・owner・結果snapshot・検証済flagを蓄積しない。

SCR019のGETごとにlocatorを読む短Web transactionを終了してからfresh MessageIDのIF030を現在API認証で呼び、API側の現在owner認可に加えてquestionId/receiptId/submittedAtを照合する。日時比較は既存wireのUTC millisecond精度へ揃え、DBの追加microsecondを誤不一致にしない。表示はこの要求で取得したAPI結果だけをHTML escapeし、request scopeへ置く。不一致・他人・削除済み・locator欠落・API確認不能は既存error処理へ進め、古いlocatorやsessionから受付成功/本文を補わない。

IF025成功後のWeb保存は3値をimmutableに登録する。同receiptの同値再登録は冪等、異なる値の競合は上書きせず非成功・診断とする。業務commitとWeb保存は別transactionなので一時欠落が起こり得る。その際、業務受付を取り消したと仮定せず、新operation tokenで質問を再生成しない。保持中の同token/同入力の正規再操作からAPIの既存確定受付結果を取得し、Web参照登録を再試行する。参照欠落のURLだけからquestionIdを推測して復元する保証はしない。

Backup/restore後もWeb値は信頼せず毎GETのAPI検証を省略しない。修復は正規APIの検証済み結果を根拠にWeb参照を合わせる片方向とし、Web参照を正として業務DBを書き換えない。Webから業務schemaへの直接接続/FK/権限は追加しない。cleanupは当日backup gateの下、業務質問が物理削除されたlocatorだけを固定保守functionで削除し、存続する質問のlocatorへ独自TTLを設定しない。実装・DDL適用・独立PTは未完了であり、QA048承認による設計条件である。
