# 移行・切替・切戻し設計

## 1. 目的

現行schubertからschubert NKへのdata移行、停止を伴う一括切替、受入、公開入口切替、切戻しおよび証跡を定める。

関連RD: MIG-001～MIG-008、MIG-DAT-001～MIG-DAT-008、SCP-101～SCP-103、FIL-003～FIL-005、TST-001～TST-005。

## 2. 移行scope

| 対象 | 方針 | 検証 |
|---|---|---|
| Scenario text | 移行 | File hash、262 file、99,661 entry基準 |
| Audio | 移行 | File hash、37,256 metadata、35,201 link基準 |
| Video | 移行 | 20 file、size/hash、Range |
| Music | 移行 | 129 file、size/hash、pair表示 |
| 検索・閲覧metadata | 再生成または移行 | DB count、constraint、代表検索 |
| 現行log | 移行しない | NK app_logsが空/初期eventだけ |
| 現行Web account | 移行しない | 新規ADMIN/USERでLogin |
| 現行physical path | 維持しない | NK root外参照0 |

## 3. 事前準備

1. 移行tool、migration、manifest生成・検証scriptをrelease candidateとして固定する。
2. 現行program/DB/materialをread-only sourceとしてinventoryする。
3. File count、総byte、全file SHA-256、DB table count、代表検索結果、Route/file順、media ID一覧を基準化する。
4. NK OS/JDK/PostgreSQL/Artemis/Caddy、service account、directory、credentialを事前構築する。
5. NK schema migrationを適用し、asset/metadataをdry run移行する。
6. 初期ADMINと必要Userを別secure手順で新規作成する。現行passwordを複製しない。
7. Characterization/IT/STを実施し、差異一覧を承認する。
8. 切戻し用の現行program、DB backup、config、Caddy/NAT値、start手順を保存する。

## 4. 移行mapping

| 現行 | NK | 変換 |
|---|---|---|
| scenario.games等6 master table | 同等table | ID維持は任意。現行ID順をdisplay_orderへ固定し、logical関係・表示順を維持 |
| app_logs | なし | 非移行 |
| Video固定list | media_assets | 223記載の20 stable logical ID、category、parent、display order、hash生成 |
| Music directory scan | media_assets | 223記載のcategory/section/pair規則で129件のdisplay orderとSHA-256 logical IDを確定保存 |
| user_pass.txt | なし | 非移行。app_usersを新規作成 |
| data/master path | asset root再配置 | Relative logical pathへ変換 |

IDを再採番する場合、entry/audio link、画面anchor、manifestの対応表を移行証跡に残す。URL bookmark互換は判定対象外。

## 5. Rehearsal

本番相当copyで最低1回、全量移行、所要時間、disk peak、失敗時再実行、DB rollback、hash検証、screen smoke、Range、
morning batch、backup/restoreを実施する。結果から本番停止枠、各step予定、Go判定期限、中止・切戻し開始時刻を承認してrunbookへ
固定する。承認した数時間の停止枠内に収まらない場合、事前copy＋停止後差分確認方式へ見直し、再rehearsalする。

## 6. 切替手順

```text
Go判定
 -> 現行公開入口停止
 -> 現行application停止・最終DB/file基準採取
 -> 最終asset/metadata移送・hash検証
 -> NK DB最終migration/load
 -> NK PostgreSQL/Artemis/API/Web起動
 -> Internal acceptance
 -> Caddy 55160公開入口をNKへ切替
 -> External acceptance
 -> Go/rollback最終判定
```

現行とNKを同時に本番公開しない。切戻し判定完了まで現行program、DB、config、assetを削除・上書きしない。

## 7. 受入check

| 分類 | 必須check |
|---|---|
| Platform | OS/JDK/PG/Artemis/app version、全unit/readiness |
| Data | File count/byte/hash、DB count、FK/CK/orphan 0、entry/file/speaker/audioのgame不一致0、表示順一致 |
| Auth | 新規USER/ADMIN Login、role拒否、session/logout |
| Current UI | Menu、全検索条件、page、Route、Scenario、audio、video、music |
| New UI | User管理、質問受付、空回答、通知、取消競合、質問回答削除 |
| MQ | Request/Reply、internal Queue、persistent、restart、DLQ/Expiry 0または説明済み |
| Media | Descriptor、root検証、200/206/416、最大1MiB |
| Operations | Backup成功、cleanup順、status、log追跡 |
| Performance | STANDARD、同時10名、p95 2.5秒 |
| Public | Global IP:55160、TLS暗号化、想定証明書警告、security header |

全必須check合格、未実施はrisk・代替・承認を記録して最終Goとする。

## 8. 切戻し判定

次のいずれかで切戻す。

- Data hash/count/FKの重大不一致
- Login、検索、主要mediaが継続利用不能
- Message取り違え、重複更新、質問消失
- Security境界違反、秘密情報露出
- 起動順・backup/recoveryの不成立
- p95目標の大幅未達で停止枠内に是正不能
- Public 55160/TLS接続不能

軽微な表示差異は差異一覧と期限・承認があればGo可能だが、要件変更を無断で許容しない。

## 9. 切戻し手順

1. Caddy公開入口を停止し、新規NK accessを遮断する。
2. NK Web、API、Artemisを停止する。
3. NKの切替後可変data（account変更、質問、通知等）を保全dumpし、破棄・再移行判断用に隔離する。
4. 現行DB、program、config、assetのhashと起動前提を確認する。
5. 現行applicationを起動し、現行Caddy/NAT設定を復元する。
6. Login、検索、Scenario、media、logの現行smokeを実施する。
7. 55160公開を再開し、外部疎通を確認する。
8. 切戻し時刻、原因、NK保全data、利用者影響、次回計画を記録する。

NKと現行は並行更新しないため、切替後にNKだけで作成された質問/account変更は現行へ自動反映できない。最終判定までは
業務利用を受入担当に限定するか、切戻し時に失われるdataを明示して承認する。

## 10. 再実行・cleanup

- 移行scriptはstaging、manifest、transactionを用いて再実行可能にする。
- 失敗したNK DBを部分手修正せず、対象schema/DBを識別して安全に再構築する。
- Go確定後も定めた保管期間まで現行backupを保持し、即時削除しない。
- 現行account file、NK credential、移送媒体はアクセス制御し、不要化後は承認手順で安全に破棄する。

## 11. 証跡

Source/target host、release commit/tag、全version、manifest hash、件数、所要時間、command終了code、試験結果、差異、
Go/rollback判定者・日時、Caddy設定backup、問題ticketを保存する。Password、秘密key、質問本文は記録しない。
