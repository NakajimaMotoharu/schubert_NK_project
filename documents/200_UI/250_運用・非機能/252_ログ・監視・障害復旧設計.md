# ログ・監視・障害復旧設計

## 1. 目的

構造化log、監査、監視mode、liveness/readiness、障害検知、systemd再起動、DLQ調査および復旧方針を定める。

関連RD: FUN-008、MON-001～MON-013、OPS-001～OPS-017、AVL-003、AVL-009～AVL-010。

## 2. Log分類

| 種別 | Producer | 主な内容 | 保存 |
|---|---|---|---|
| REQUEST | Web | HTTP method/path/status/elapsed/request ID | JSON file/journald＋WLGEVT01経由DB投影 |
| ACTION | Web/API | Search、閲覧、media、質問、管理操作 | API側DB audit＋各process JSON log。MENU_VIEWEDだけUI235の限定Web投影 |
| SECURITY | Web/API | Login、lock、role、session、権限拒否 | DB＋JSON log |
| MQ | Web/API | Send/receive/ACK/retry/DLQ、message相関 | JSON log、重大eventはDB |
| SYSTEM | 全component | 起動、停止、health、resource、exception要約 | Journald/JSON |
| BATCH | Morning batch | Step、件数、byte数、backup/cleanup結果 | DB＋JSON log |

Web REQUESTはresponse確定時にlocal JSONへ記録し、同じevent Message IDの`WLGEVT01`をtechnical outboxからAPIへ送る。
APIは`app_logs.source_message_id`で冪等INSERTする。これによりLog画面のHTTP項目とWeb/API分離を両立する。投影遅延・失敗時も
local JSONを失わず、outboxのPENDING/ERROR件数と最古滞留時間を監視する。認証、User更新、質問削除等のcritical auditは
API transaction内のDB記録を正とし、WLGEVT01へ代替しない。

## 3. 共通field

`timestamp`、`level`、`service`、`appVersion`、`eventType`、`action`、`requestId`、`messageId`、`correlationId`、
`jmsMessageId`、`receiptId`、`username`、`role`、`remoteAddress`、`httpMethod`、`path`、`status`、`elapsedMs`、
`deliveryCount`、`resultCode`、`errorCode`を該当時に設定する。

改行・TABをspaceへsanitizeし、1 event 1 lineのJSONとする。時刻はUTC ISO-8601で保存してもよいが、画面はJSTへ変換する。

### 3.1 Current/NKログ比較の限定変更（QA-051/UIC-010、2026-11-02承認）

NKのaction/categoryはSS351のcatalogを正とする。Currentの旧名称との対応と、既存ログ保全・今回操作の相関付き安全投影によるCHR-L01比較はUI264 §5.1/SS355 §8.1に従う。比較対象の投影方法を変えても、local/outbox/DBの欠落・重複0、業務/security監査のDB正本、秘密情報除外、既存ログ保全を緩めない。

追加技術行は既存承認設計に基づく期待表で個別検証し、任意の追加category/件数を免除しない。既存ログやCurrent baselineを変更して一致させない。実装/比較試験/工程受入は本承認とは別に未完である。

## 4. 機微情報除外

次をlog、metric label、exception message、thread name、Queue propertyへ出力しない。

- Password、password hash、DB/MQ credential、暗号key
- 認証context IDのraw/hash/ciphertext、session cookie、CSRF token
- 質問本文、回答本文、full request/response fixed body
- File physical absolute path、backup暗号内容
- User-Agent全文をmetric labelへ使用すること

Username、receipt ID、logical media IDはaccess制限されたauditで必要最小限記録する。Debug modeでも除外規則を変更しない。

## 5. 監視mode

| 項目 | DEBUG（PG/PT/IT） | STANDARD（ST/本番） |
|---|---|---|
| Liveness/readiness | 有効 | 有効 |
| Systemd/journald | 有効 | 有効 |
| Artemis管理・Queue | 有効 | 有効 |
| PostgreSQL統計 | 有効 | 有効 |
| Disk/backup/batch | 有効 | 有効 |
| Actuator詳細metric | 有効 | 無効 |
| Prometheus/Grafana/exporter | 有効 | 停止 |
| Metric保存 | 15日、5GB上限 | なし |
| Application log level DEBUG | 別設定。必要時だけ | 原則INFO |

`MONITORING_MODE=DEBUG|STANDARD`を外部設定し、application rebuildなしで切替える。Modeと監視serviceの起動状態が不一致なら
status checkを失敗させる。

外部通知先は初期要件に含まれないため、local status、journal、管理画面/SSH確認を正とする。将来通知先を追加しても業務通知tableへ混在させない。

## 7. Liveness・readiness

- Livenessはprocess自身がevent loop/workerを応答できることだけを判定し、依存component停止でprocessを無限再起動させない。
- ReadinessはWebのMQ/session store、APIのMQ/DB/root、Artemis journal/Queue、DB migration versionを含む。
- Health endpointはloopbackと許可されたservice accountだけ。秘密値、version詳細、exceptionを返さない。
- CaddyはWeb readiness false時に503 maintenance messageを返す。

## 8. Systemd再起動

Web/APIは`Restart=on-failure`、`RestartSec=5s`、10分に5回までを初期値とする。正常stop、計画停止、exit code 0は再起動しない。
Restart抑止時はunit failed、last exit code、message ID、原因分類をstatusへ表示する。

固定長/protocol errorでは対象messageをDLQへcommitしてからexitするため、再起動後に同一不正messageを再取得しない。
DLQ移送自体が失敗した場合は元messageをACKせずexitし、rate limitで無限loopを抑止して運用介入を待つ。

## 9. 障害別復旧

| 事象 | 検知 | 自動処理 | 運用復旧 |
|---|---|---|---|
| Web停止 | systemd/HTTPS | 5秒後再起動 | Log、MQ reply、session store確認 |
| API停止 | systemd/Consumer 0 | 再起動、未ACK再配送 | DB/MQ/root確認 |
| Artemis停止 | unit/Queue health | systemd再起動 | Journal/paging/disk検証 |
| DB停止 | pg readiness | PostgreSQL policy | DB log、disk、recovery。Appはdeny closed |
| Protocol error | DLQ＋exit | App再起動 | Layout/version/producer修正後に個別再投入 |
| Backup失敗 | batch result | Business削除skip、App起動継続 | Root容量/permission/DB接続修正、再実行 |
| Transfer個別file清掃失敗 | batch result `WARNING` | Rootが安全ならApp起動継続、容量監視 | Path/type/permission修正、対象を再清掃 |
| Transfer root検証失敗 | batch result `FAILED` | 後続起動停止、Caddy非公開 | Root重複/mount/permission修正後に朝処理再実行 |
| Expiry保守失敗 | batch result/Queue件数 | Critical未満は警告継続、以上はAPI起動停止 | Credential/Broker/selector修正後に保守step再実行 |
| Web log投影停止 | outbox/Queue最古時刻 | Local JSON継続、dispatcher/ingestor再試行 | DB/MQ/codec修正後にevent Message ID重複0を確認 |
| Disk枯渇 | threshold | Result生成停止 | 保全後にlog/expiry整理または容量拡張 |
| Media欠落/hash差異 | Descriptor/read error | 配信拒否 | Manifest正本から復元 |

## 10. DLQ運用

1. Browseだけでoriginal Address、layout、Message ID、error code、delivery countを確認する。
2. Producer version、body hash、同種件数、業務commit有無を調査する。
3. 原因を修正し、再処理が安全かrequest_inboxで確認する。
4. 対象Message IDを指定して1件または承認件数だけ再投入する。
5. 成否と新transport IDを記録し、元DLQ messageを成功確認後に削除する。

Internal workのDLQでは受付ID/Job IDをbodyから安全にdecodeし、DBの`async_jobs`/`notifications`と必ず照合する。最終失敗が
DBへ反映済みなら`ERROR`とerror通知を確認する。DB障害でBrokerだけがDLQへrouteして状態未確定なら、原因復旧後に
（a）同じMessage IDで安全に再投入、または（b）job/notificationを`ERROR`へ同一transactionで確定、のいずれかを承認記録付きで
実施する。DB状態を`RECEIVED`/`PROCESSING`のまま放置して元DLQを削除してはならない。

Bodyを端末へ不用意にdumpしない。Passwordを含むLogin requestはDLQ accessを特に制限し、調査後に安全に削除する。

## 11. 保存・rotation

- Application file logは100MB×14世代を基本とし、service合計5GB以内。
- Journaldはsize/time上限を設定し、無制限増加させない。
- DB app_logsの初期保存期間は90日、朝batchでbackup成功後に期限削除する。Session、inbox/outbox、batch runを含む詳細条件は
  251 §6を正とする。Security auditの延長が必要な場合は変更管理する。
- DEBUG metricは15日・5GB。STANDARD切替時に不要serviceを停止するが、証跡として必要な試験metricはarchiveする。

## 12. 定常確認

毎日、全unit、HTTPS、readiness、Queue/DLQ/Expiry、DB接続、disk、last backup、last batch、restart回数を確認する。
Release後・障害後はMessage/Correlation IDでBrowserからAPI transactionまで追跡できることをsample確認する。

## QA-054の保存責務（UIC-011、2026-11-05承認）

MENU_VIEWEDは認証済み正常メニューGETの成功終端時にWebで一度生成し、REQUESTと別eventとして既存local/outbox/API DB投影へ流す。HTTP request IDで同じ操作へ対応させ、source_message_id UKで再送重複0を保証する。critical監査のDB正本をこの投影へ置換しない。

LOG_SEARCHEDはADMINのログ検索がAPIで初回成功確定するtransactionに一度保存する。検索結果snapshotを取得した後の監査であり、その応答に自身の後発監査が含まれないこととDB保存欠落を区別する。保存済み結果の再送で同業務処理・成功ACTIONを重複発行しない。INBOX_REPLAYEDは別MQ記録であり成功ACTIONを代替しない。local/outbox/DB、API transaction、再送、観測時点をUI264/SS355の独立期待表で検証する。
