# 性能・容量・可用性・セキュリティ設計

## 1. 目的

同時利用者10名、16GB memory、256GB SSD、単一serverでの性能budget、容量配分、可用性目標、security controlを定める。

関連RD: ENV-001～ENV-004、PER-001～PER-010、AVL-001～AVL-010、SYS-008～SYS-014、FIL-001～FIL-009、BAK-005～BAK-007。

## 2. Performance目標

| 対象 | 目標・上限 |
|---|---|
| 同時利用者 | 最大10、通常5未満 |
| 通常同期画面 | 打鍵から表示完了p95 2.5秒以内 |
| WebのMQ reply待ち | 2.0秒 |
| Media | Range response開始までを測定。File全転送時間は除外 |
| Scenario検索/log | 100件/page |
| 新規一覧 | 50件/page |
| Internal async | Consumer 1、FIFO、business timeoutなし |

計画停止、起動直後、障害注入、media全file転送を2.5秒対象から除外する。成功responseだけを恣意的に抽出せず、timeout/error率も併記する。

## 3. 同期time budget

| 区間 | p95 budget |
|---|---:|
| Browser～Caddy～Web入力 | 150ms |
| Web encode/send | 100ms |
| Queue待ち＋API decode/auth | 150ms |
| API業務/DB | 1,400ms |
| Reply＋Web view生成 | 400ms |
| HTML転送・Browser描画 | 300ms |
| 合計 | 2,500ms |

Web reply timeout 2.0秒はMQ/API区間の上限であり、p95 budget超過を早期検知する。DB queryは機能別statement timeoutを
2秒未満で設定し、更新transactionは短時間にする。

## 4. Concurrency・pool

| Resource | 初期値 | 上限 |
|---|---:|---:|
| Web HTTP worker | 16 | 32 |
| Web同期MQ同時待機 | 12 | 20 |
| API sync Consumer | 4 | 8 |
| API async Consumer | 1 | 1 |
| API DB pool | 8 | 8 |
| Batch DB connection | 1 | 1 |
| 同時media stream | 20 | 20 |

Queue Consumerを増やしてDB poolを超過させない。Overload時は無制限thread/Queueを作らず、入口で503/429相当と再操作案内を返す。

## 5. Memory budget（16GB）

| 用途 | 初期上限 |
|---|---:|
| OS、filesystem cache、Caddy/systemd | 3GB |
| PostgreSQL | 4GB |
| Artemis JVM/direct memory | 2GB |
| API Java | 2GB |
| Web Java | 1.5GB |
| DEBUG監視component | 2GB |
| Safety margin | 1.5GB |

STANDARDではDEBUG監視2GB分をheadroom/cacheへ戻す。Java heapだけでなくdirect buffer、thread stack、class metadataを含む
systemd `MemoryMax`を設ける。値はIT負荷試験とGC logで下方/上方調整するが合計16GBを超えない。

## 6. SSD容量budget（256GB）

| 用途 | Budget |
|---|---:|
| OS/package/release | 45GB |
| Business asset（現行約19.3GB＋余裕） | 35GB |
| PostgreSQL data/index/WAL | 30GB |
| Artemis journal/paging | 10GB |
| Transfer root | 5GB |
| Log/journald | 10GB |
| Local backup 7世代 | 80GB |
| DEBUG metric | 5GB |
| Free/headroom | 36GB |

Backup実sizeが80GBを超える前にNASまたは容量拡張を行う。同一SSD内backupはSSD故障を保護しない。Filesystem 80% warning、90% critical。

## 7. Queue・file容量

- Web/API Request/Replyは最大1,000,000 byte、質問workは1,000 byte、Web log eventは10,000 byte。
  Async Queue 10,000件/1GB、Web log Queue 10,000件/256MB、DLQ 2GB、Expiry 1GB。
- Large-result 1件48MB、transfer root 5GB。取得成否にかかわらず翌朝削除。
- Async requestはbusiness timeoutなしのため、滞留件数・diskを監視し、上限接近時は新規質問受付を`9001`で停止する。
- 既受付jobを容量都合で自動削除・expireしない。

## 8. 可用性

| 項目 | 設計 |
|---|---|
| 構成 | 単一server・単一broker・単一DB。無停止HAなし |
| 計画停止 | 毎日05:00頃、数十分を許容 |
| Process障害 | systemd on-failure restart、rate limit |
| 非同期回復 | Durable Queue、outbox/inbox、冪等性 |
| RPO/RTO | ともに24時間目標 |
| Backup | 毎朝1回、7世代、復元試験 |
| 物理故障 | 別保存master＋local backup。Local SSD同時故障riskを受容 |

Sync停止中は再操作可能errorとし、更新処理はoperation tokenで結果不明を回復する。HAが必要になった場合は別要件変更とする。

## 9. Network・TLS

- 外部公開はglobal IPの55160/tcpだけ。Web、API、MQ、DB、管理consoleを公開しない。
- CaddyがTLS終端し、初期は内部証明書による警告を許容する。暗号化自体は維持する。
- 証明書警告により接続先真正性を利用者が検証しにくいriskを運用案内へ明記する。
- Domain/公的証明書へ移行するときはCaddy site/証明書だけを変更し、application/MQ interfaceを変更しない。
- Caddyからのforwarded headerだけを信頼し、外部headerを上書きする。

## 10. Application security

| 観点 | Control |
|---|---|
| Authentication | DB hash、Login rate limit、context ID hash、8時間idle、最大2 session |
| Authorization | Web/API二重role・owner検証、deny by default |
| Browser | CSRF、CSP、HSTS、frame拒否、nosniff、SameSite/Secure/HttpOnly |
| Input | NFC、byte上限、allowlist、control文字禁止、parameter binding |
| File | Logical ID、root検証、symlink/root外拒否、size/hash |
| MQ | Loopback、service別user、least privilege、fixed protocol validation、DLQ |
| DB | Role分離、prepared statement、FK/CK、migration role分離 |
| Secret | Git禁止、0600、service別credential、log redaction |
| Audit | Login、権限拒否、管理更新、質問削除、MQ/DLQ追跡 |

Web log outbox payloadと更新request fingerprintは外部keyによるAES-GCM/HMACを使用し、Passwordや入力本文をtechnical schemaへ
保存しない。Operation token再送はowner/layout/target/payload一致時だけ冪等成功とする。

## 11. Security update・dependency

日次一般`apt update/upgrade`を計画停止で実行する。緊急security updateの選定は別project所管だが、本projectのstop/start、
backup、smoke testへ接続できること。Java/Maven dependencyはCIで脆弱性検査し、release時のversion manifestを保存する。

## 12. 試験・判定

- STANDARD modeで同時10名が各1同期requestを実行し、p95、error率、取り違え0を確認する。
- Search worst case、Scenario file mode、Log 100件、通知/質問50件、20 media streamを個別/組合せで測定する。
- Broker/DB/API/Web停止、再配送、DLQ、OS reboot、backup/restore、disk閾値を試験する。
- Password/token/質問本文がlog/metricへ出ないこと、USERがADMIN/他人dataへaccessできないことを確認する。
