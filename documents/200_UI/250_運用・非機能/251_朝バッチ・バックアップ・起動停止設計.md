# 朝バッチ・バックアップ・起動停止設計

## 1. 目的

毎日05:00頃の計画停止、package update、OS再起動、PostgreSQL、backup、業務data削除、transfer清掃、Artemis、
Expiry保守、API、Web、Caddyの依存順を定める。

関連RD: AVL-001～AVL-008、OPS-001～OPS-017、BAK-001～BAK-008、BKO-001～BKO-008。

## 2. Unit構成

| Unit/target | 種別 | 責務 |
|---|---|---|
| `schubert-nk-maintenance.timer` | timer | 毎日05:00 JSTに停止・update・rebootを開始 |
| `schubert-nk-maintenance.service` | oneshot | Lock、入口停止、app停止、apt、reboot要求 |
| `schubert-nk-morning.target` | target | Reboot後の朝処理と依存順を束ねる |
| `schubert-nk-backup.service` | oneshot | DB/config backupと検証 |
| `schubert-nk-cleanup.service` | oneshot | 条件付きbusiness data削除、transfer清掃 |
| `artemis.service` | service | Broker |
| `schubert-nk-expiry-cleanup.service` | oneshot | 7日を超えたExpiry messageの件数・byte記録と削除 |
| `schubert-nk-api.service` | service | API Java |
| `schubert-nk-web.service` | service | Web Java |
| `caddy.service` | service | 公開入口 |

PostgreSQL/Caddyのdistribution unitを使用し、独自targetから`After`/`Requires`/`Wants`を設定する。通常bootで各serviceが
勝手に並列起動しないよう、schubert NK用起動をmorning targetへ集約する。

## 3. 計画停止前半

1. 排他lock `/run/schubert-nk/maintenance.lock`を取得する。取得済みなら二重実行せず失敗記録。
2. Maintenance開始、version、disk、Queue、未処理job、Login利用者数を記録する。
3. Caddyの公開siteを停止またはmaintenance responseへ切替え、新規業務requestを遮断する。
4. Web Javaをgraceful stopする。新規MQ requestを止め、最大30秒で待機responseを終了する。
5. API Javaをgraceful stopする。新規Consumer取得を止め、処理中transactionを最大60秒待つ。未完了はrollback/requeueする。
6. Artemisを停止しjournal flushを確認する。
7. PostgreSQLをclean stopする。
8. `apt update`、`apt upgrade`を実行し、変更packageと終了codeを記録する。
9. OS rebootを実行する。

Stop順は`Caddy -> Web -> API -> Artemis -> PostgreSQL`。Processを自動`kill -9`せず、timeout時はunit失敗・証跡保存後に
運用規則で強制終了可否を判断する。初期空回答stubは60秒以内に完了できることをPTで確認する。

Package update失敗時もservice復旧を優先してrebootと朝起動を継続し、update失敗を警告する。Kernel/packageの破損等で
rebootが危険と判定された場合だけ自動rebootを止め、公開入口を再開せず運用介入を待つ。

## 4. Reboot後の実行順

```text
1 PostgreSQL start/readiness
  -> 2 DB/config backup + validation
       ├─ success -> 3a business data cleanup
       └─ failure -> 3b business data cleanup skip
  -> 4 transfer file cleanup（backup成否にかかわらず）
  -> 5 Artemis start/readiness
  -> 6 Expiry Queue retention cleanup
  -> 7 API Java start/readiness
  -> 8 Web Java start/readiness
  -> 9 Caddy start/public smoke check
```

PostgreSQL readiness失敗時は2以降を実行せず、Caddyを公開しない。Backup失敗時はbusiness data削除だけをskipし、
transfer清掃とapplication起動を継続する。

## 5. Backup

### 5.1 対象・方式

| 対象 | 方式 |
|---|---|
| PostgreSQL可変data | `pg_dump -Fc`。DB全体またはschema一貫dump |
| Config | 非秘密設定＋暗号化したcredential archive |
| Version情報 | OS/JDK/PostgreSQL/Artemis/app/schema version manifest |
| Master asset | 定常backup対象外。別保存済み正本とSHA-256 manifestから復元 |

Backup directoryは`yyyyMMdd-HHmmss`の一意名へ作成し、`.part`から確定名へatomic renameする。Dump command終了0、非0 byte、
`pg_restore --list`成功、SHA-256作成・照合を成功条件とする。
`pg_dump -Fc`は専用`schubert_backup` role/credentialで実行し、`schubert`、`schubert_web_session`、
`schubert_meta`のdump対象だけを読む。`schubert_batch`でdumpせず、backup roleへDML/DDL/SET ROLE/復号keyを与えない。

### 5.2 世代・失敗

- 日次7世代。新規backup検証成功後だけ8世代目以降を古い順に削除する。
- 新規backup失敗時は既存世代を削除しない。
- Backup先は初期local別directory。同一SSD故障を保護できない制約を運用画面/手順へ明記する。
- `backup.root`変更だけで将来NASへ切替可能とする。NAS障害時のtimeoutとlocal fallbackは勝手に行わない。
- 月次またはrelease前に別test DBへrestoreし、RTO 24時間以内を実証する。

## 6. Business data cleanup

当日backup成功時だけ、単一batch run IDの下で次を順に行う。

1. `COMPLETED`かつstate_changed_atから24時間以上のnotificationを削除。
2. `ERROR`かつstate_changed_atから24時間以上のnotificationを削除。
3. `CANCELLED` notificationを削除。
4. `is_deleted=true`かつ関連notification不存在のquestion/answerを物理削除。
5. 期限切れsession、log、inbox/outbox等の技術dataを次表の保持方針に従って削除。

`RECEIVED`/`PROCESSING` notificationは削除しない。対象件数、削除件数、失敗件数をstepごとに記録する。Question/answerは
aggregate単位transactionで削除し、FK RESTRICT違反はskip・警告として保持する。

| 技術data | 自動削除条件（run開始cutoff基準） | 削除しないもの |
|---|---|---|
| `auth_sessions` | revoked/expired後24時間以上 | 有効session |
| `web_http_sessions` | `expires_at`経過 | 有効session |
| `pending_context_revocations` | IF-002成功、またはAPI expiry確認済み | 未失効で再試行中 |
| `login_ip_attempts` | Window/lock終了後24時間以上 | 有効window/lock |
| `request_inbox` | 参照系完了後24時間、更新系完了後7日を`expires_at`へ設定し経過 | PROCESSING、結果不整合 |
| `mq_outbox` | SENT後7日 | PENDING/ERROR |
| `web_log_outbox` | SENT後7日 | PENDING/ERROR |
| `app_logs` | `logged_at`から90日超 | 90日以内。延長対象security audit |
| `batch_runs` | 完了から400日超 | RUNNING/FAILED調査中、400日以内 |

保持値はRDの容量枯渇防止を具体化する初期値である。削除前に当日backup成功を必要とし、件数・最古/最新日時を記録する。
`request_inbox`削除後もquestionsのowner＋operation token一意性等、業務table側の重複防止を破壊しない。保持延長は可能だが、
短縮時は再送・監査・障害復旧への影響を変更管理する。

### 6.1 Inbox整合性検査（UIC-006/QA-046、2026-09-09承認）

当日backup成功後のcleanup内部で、非公開の検査専用processを実行する。通常API/Webは停止したままとし、Broker/API通常起動を先行させない。batchへ秘密鍵を渡さず、検査processだけが必要最小限の読取り権限・暗号鍵を使用する。復号、保存応答の構造、owner/result参照の整合を検査し、検査不能・欠落・不整合行を削除せず警告する。検証と削除の間に対象が変化した場合は再検証または保持とし、過去の検証済flagだけで削除しない。既定のbackup gate・保持期間・cleanup順は変更しない。

## 7. Transfer cleanup

- Backup成否にかかわらず実行する。
- Batch開始時点で存在するtransfer root配下の`.part`/`.ready`を対象にする。
- Regular fileだけを削除し、symbolic link/device/socketは削除せず異常記録する。
- 削除件数、byte数、失敗pathのlogical IDを記録する。
- 個別fileの削除失敗は`WARNING`として記録し、root自体が安全かつ書込み可能なら後続起動を継続する。
- Root不正、rootがasset/backupと重複、mount異常または書込み不可を検知した場合は1件も削除せずunitを`FAILED`とする。
  この場合は後続のArtemis/API/Web/Caddyを開始せず、公開入口を停止したまま運用介入を待つ。

## 8. Expiry Queue retention cleanup

- Artemis readiness後、API/Web Consumer起動前に`schubert-nk-expiry-cleanup.service`を実行する。
- `nk_mq_maintenance`の限定管理権限で、Brokerが保持するexpiry日時を基準に7日を超えたmessageだけをselector purgeする。
- 実行前後件数、対象件数、削除件数、推定byte数、失敗件数、cutoff日時をbatch runへ記録する。
- Queue/journal fileをOSから直接削除せず、Artemis管理API経由で削除する。DLQは対象外とする。
- Purge失敗時は`ERROR`を記録する。Expiry件数がCritical未満なら業務起動を継続し、Critical以上またはBroker health不良なら
  API以降を開始せず運用介入を待つ。

## 9. 起動・readiness

| Component | Start timeout | 成功条件 |
|---|---:|---|
| PostgreSQL | 120秒 | `pg_isready`、migration version、read/write probe |
| Backup | 30分 | Dump・manifest検証 |
| Cleanup | 30分 | Root検証成功、各step結果記録。個別file失敗は`WARNING`、root異常は`FAILED` |
| Artemis | 120秒 | Journal、Queue、acceptor、disk正常 |
| Expiry cleanup | 10分 | 7日超selector purge結果記録。Critical未満の失敗は警告継続可 |
| API | 120秒 | DB/MQ/root、Consumer、codec readiness |
| Web | 120秒 | MQ reply Consumer、session store、HTTP readiness |
| Caddy | 30秒 | Config validate、Web upstream、HTTPS `/login` 200 |

API/Web/Caddyの後段失敗時は後続を開始しない。Caddy smoke checkはloopbackと到達確認済みglobal IPの双方を運用可能な範囲で行う。

## 10. 手動操作

`start`、`stop`、`restart`、`status`、`morning-run`、`backup`、`restore-test`、`logs`をwrapper scriptで提供する。
Scriptは対象unit、前提、実行user、timeout、終了codeを統一し、二重起動を拒否する。Statusは全component、Queue、DLQ、
last backup、last morning run、disk、公開HTTPSを1回で確認できること。

## 11. 再実行

- `batch_runs`のbusiness date/step状態を確認し、成功済みstepを冪等skipする。
- Backupは再実行ごとに一意directoryを作り、成功した最新1件を当日成功とする。
- Cleanupは条件付きDELETEにより再実行可能。既削除件は0件成功。
- Transfer cleanupも不存在を成功扱いにする。
- Expiry cleanupは同一cutoffを再利用し、既削除messageを0件成功として冪等に扱う。
- 途中失敗後の再実行が翌日対象を誤削除しないよう、判定基準時刻をrun開始時に固定する。

## 12. 証跡

Run ID、開始/終了、host、version、担当/自動unit、step、command要約、対象/成功/失敗件数、byte数、終了code、
backup manifest、error要約を保存する。Password、credential path内容、質問本文を記録しない。

## QA-048承認反映：受付参照のbackup・cleanup（2026-10-03）

受付参照tableはWeb technical schemaの一貫dump/restore対象に含め、専用backup roleへ明示SELECTを与える。保存対象は検証済IF025の3値だけである。通常API/Web停止・当日backup成功・既定cutoff/lockの下、業務質問が物理削除済みのlocatorだけを固定保守functionでchunk削除し、件数・skip/失敗を分けて記録する。business question存続中はlocatorを独自TTLやWeb session期限で消さない。business削除直後やrestoreでWebに孤児が一時残ってもSCR019の毎GET API検証で本文/成功表示を拒否する。restoreは業務側を正とし、Web参照から業務質問を再生成しない。新しい保持日数や通常API先行起動は採用しない。詳細はSS331 §9.4/SS341末尾のQA048補足、実配備/PTは未完了。
